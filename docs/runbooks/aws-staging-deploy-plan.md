## Scope and hard limits (owner decision 8, CLAUDE.md environment safety)

One deployment of one **named commit** to AWS **staging only**, after the A-class software work. `APP_ENV=staging` (the Terraform module refuses `production`).
**No production** environment or data, **no real money**, **no real customers**, **no production credentials**, **all providers MOCK**, synthetic data
only, one region (`eu-central-1`), the one account pinned in the staging root's `allowed_account_ids` (Terraform refuses any other; using a different
account is a code change and a new decision). Purpose: verify, in this order, what the local drill could not: runtime roles, `search_path`, secrets,
database permissions, migrations, **PITR restore to a timestamp**, **logical backup and restore**, deployment, observability and alert delivery.
It does not demonstrate technical production readiness by itself (CI and local evidence are separate), legal readiness or provider readiness.
Any unexpected result means **STOP and report**: no workaround, no privilege escalation, no production credential, no real data.

**Actor-proof row (was owner action B; automated by `deploy.sh runner seed-actor-proof`).** The reviewed procedure is still `operational-runbooks.md` section 15 step 4 (a parameter-bound
`INSERT INTO actor_proof_keys (kid, secret) VALUES ($1, decode($2, 'hex'))` as the table owner); the runner mode performs exactly that, from the VPC-resident task, with no human handling the key.
It runs in its OWN task definition (`staging-runner-actor-proof`: the master password and `ACTOR_PROOF_KEYS` injected by the execution role, NO task role, so no AWS credential in that container). It parses the
`igaming-staging/actor-proof-keys` value (`stg-v<N>:<base64>`), requires the kid to equal `ACTOR_PROOF_ACTIVE_KID` (Terraform output `key_family_kid`), decodes to >= 32 bytes, hex-encodes into a 0600 file on tmpfs, and sends it as a
BOUND parameter (`\bind`) from a script file (never a command line, `-v` option, URL or statement text). It first refuses if the server could log the parameter (`log_statement` mod/all,
`log_min_duration_statement`, `log_duration`, `log_parameter_max_length_on_error`, pgaudit parameter logging: the runbook's pre-check). It is idempotent without overwriting: an identical row is reported, a different secret for the same
kid STOPs the run (rotation stays a reviewed manual procedure), only an absent kid is inserted. It refuses unless `APP_ENV` is `development` or `staging`. It reports kid / status / octet length only
(48 bytes, `active`). Until the row exists every governed write (K1/K2/K3, launch decisions, RG floors) is refused with `AP002`, which makes acceptance flow 6.6 for those features fail: the designed fail-closed state.
**Residual accepted for staging (SRSP-9 in the record):** the key is in the task's PID 1 environment (as every ECS-injected secret is) and in one tmpfs file for the duration of the run; the database log is protected by the pre-check, not by masking.
**After a LOGICAL restore** the same insert is done by `deploy/backup/rekey-actor-proof.sh` (step 8.3) with a NEW kid: the logical dump EXCLUDES `actor_proof_keys.secret` (owner decision 5).

**Operating-market rows (was owner action C; automated by `deploy.sh runner seed-market`).** No route, console or tool wrote them (ADR 0045: zero routes). STAGING-PREP-3 adds `cmd/seed-market`, the one-off Go call the runbook
(`market-blocking-configuration.md` sections 2 and 3) describes: it resolves the synthetic tenant and brand by slug, then calls `operatingmarket.CreateLicenceCountryCeilingVersion` (platform-admin transaction) and
`CreateOperatingCountryPolicyVersion` (tenant transaction, tenant scope) with a MANDATORY `AuthorizationReference`; the library writes the audit rows in the same transactions (actor = the sole active platform admin, or `ACTOR_ID`).
Parameters: `TENANT_SLUG`, `BRAND_SLUG`, `COUNTRY` (must equal `mock_geolocation_country` when that is set; if unset, the residence recorded for the test players), `AUTH_REF`, `OPERATOR`, `REASON`, optional `ACTOR_ID`, `DRY_RUN`. It is idempotent (an identical open version is left alone), refuses to re-enable a closed
country, refuses any `APP_ENV` other than development/staging, and afterwards re-resolves registration, deposit, casino and sportsbook wagering for the brand and fails unless every one is permitted. The tenant, its licence and the brand must
already exist (created through the Back Office after `seed-admin`). **MKT-DUAL-1 (four-eyes on market enablement) is still OPEN: two humans review the parameters and the authorisation reference by process and record both in the change ticket.**
Until the rows exist the market gate refuses registration, deposit, casino launch and sportsbook placement (`403 MARKET_NOT_AVAILABLE`) and `launch-readiness` shows `R-MARKET-CONFIG` failing. With `mock_geolocation_country` unset (owner decision 3: the default) the deposit/launch/placement flows additionally need, per test player, an approved MOCK-KYC verification with a reviewer-recorded `verified_residence_country` (and `verified_residence` evidence collection activated for the tenant); registration needs only the market rows. `seed-world` (6.4) writes the market rows for its synthetic tenants too.

## 13. Teardown (same window; the new protections make it multi-step)

1. Confirm section 12 evidence is captured and the owner allows teardown (or a stop condition requires it).
2. Lift protection deliberately: `deploy.sh up -var db_deletion_protection=false` (interactive), or edit the git-ignored tfvars.
3. Choose a unique final snapshot name if one from an earlier deploy exists: `-var db_final_snapshot_identifier=igaming-staging-db-final-<short-sha>`.
4. `deploy/aws/scripts/deploy.sh down` (interactive destroy; takes the final snapshot, then runs `verify-teardown.sh`). If it stops on a `DependencyViolation`, wait and re-run (`stage-9-4-staging-lifecycle-runbook.md` section 6).
5. `verify-teardown.sh` will list the final snapshot and retained automated backups. **Delete them once the evidence is recorded** (`aws rds delete-db-snapshot ...`, `aws rds delete-db-instance-automated-backup ...`), then re-run it to a clean result. Delete the PITR clone if 7.5 was not done.
6. Session-end security check: no ACTIVE Access Analyzer finding (`stage-9-4-staging-lifecycle-runbook.md` section 6).
7. Remove local secret material from the runner (signing private key copy, decrypted scratch, token files); the state bucket and the budget remain by design.
8. Record in the evidence file: leftovers, time to destroy, total elapsed hours (cost model: `stage-9-4-staging-lifecycle-runbook.md` section 7).

The retained pieces are a deliberate consequence of A12 (deletion protection, final snapshot); the older statement in the lifecycle runbook that RDS leaves no final snapshot predates it.
