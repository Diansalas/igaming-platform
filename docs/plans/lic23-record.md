## 2. N-2 design and the owner-visible decision

**Decision for the owner (legal policy for sanctions false positives).** A sanctions match found by the system is resolved only by recording it (which places a hold) and lifting that hold by the proof-bound four-eyes approval (two distinct officers, neither the recorder as the executing approver). After the lift the person counts as reviewed-and-cleared from the lift time. The platform does not decide whether that is legally sufficient, how long a review stays valid, or whether a second, independent reviewer outside the officer pool is required: those are the owner's. **As built, a review does not expire**: the identical hit is recognised as already reviewed for as long as the person exists. If policy requires periodic re-review, a maximum age of the review must be added (a configuration value the platform would not default).

**Identical hit.** The worker builds a keyed pseudonymous fingerprint of a match: HMAC-SHA256(tenant subject key, "match-fp:v1:" + the sorted `list:vendor-match-reference` pairs), only when EVERY match carries a vendor reference (`ScreeningMatch.VendorMatchRef`, which was never persisted: still not; only the fingerprint is). `aml_screening_request_finish` compares it with earlier `needs_officer` requests of the same person that are reviewed-and-cleared (or that were themselves auto-reviewed) and, on a match, stores `reviewed_from_request_id`. Such a request is final as `needs_officer` but counts as resolved and as a fresh screening at its completion time; it raises no attention alert. A different hit, or a provider that gives no stable reference, needs an officer again. The mock derives its match reference from the marker suffix (`SYNTH-SANCTION-1` and `-2` are different hits). **Privacy:** this adds a pseudonymous per-person value derived from vendor match references to the queue table; it belongs on the Q6 privacy review before any real provider.

The PEP "accepted match" path is the same mechanism (record the match, a second officer lifts the hold); the existing single-officer clear of a non-sanctions match remains.

## 3. Operator runbook additions (MOCK environments only)

- Switch a gate off after a licence rebind or basis closure: POST a trigger-policy version with `gate_withdrawal=false` and an empty `events` list for the SAME jurisdiction (N-1).
- Un-stick a person: GET `.../screening/persons/{id}/requests`; a `pending`/`claimed` request that is stale: POST `.../requests/replace` with its `request_id` and a reason code; a person with no request: the same call without `request_id`. A request in `needs_officer`/`failed_terminal`: resolve it (`.../resolution`).
- Clear a sanctions false positive: resolve the request with `potential_match` + `match_lists:["sanctions"]` (hold placed), then lift by the case four-eyes (`lift_hold` proposal and approval). The next identical re-screen does not hold the person again.
- A gate can be enabled only where the database environment anchor (written once by the owner) says development, staging or test. A database with NO recorded anchor is production for every guard.
- Rebuild, never roll back, a database that applied 0181 before these edits (section 0).

## 4. SN-3 (RG): exactly what is missing

RG is selected by the tenant's licence jurisdiction in `internal/rg` (`limits_service.go` tenantJurisdiction, used by `enforcement.go`, `limits_config.go`, `limits_service.go`, `limits_timeout.go`, `limits_usage_inputs.go`, `options.go`) and by the migration 0135 ceiling trigger. Scope-aware selection needs: (1) the player's verified residence country in the same transaction (`kyc.ReadMarketResidenceEvidence`, the KYC technique), (2) an operation mapping per control kind (deposit limit: deposit; loss / wager: wagering; time-out and self-exclusion: all), (3) `operatingmarket.ResolveRulebookJurisdiction` per call, (4) the same selection inside the SQL ceiling trigger (a trigger cannot call Go), and (5) the readiness and activation guard evaluating the floors of every governing jurisdiction. Items 4 and 5 are a redesign of the RG write path and were not attempted. Using the STRICTER of two jurisdictions' limits was rejected: "stricter" across independent regimes is a value judgement the platform must not invent. Today: a basis-only tenant fails closed at runtime and fails R-RG-CONFIG (`no_licence_jurisdiction`: **R-RG-CONFIG does block such a tenant from launch**); a licence-plus-basis tenant uses the licence jurisdiction's RG rules (possibly weaker than a basis jurisdiction's) and now shows the acknowledgeable `bases_present_licence_rulebook_only` note.

## 6. Residuals

1. **Review validity has no expiry** (section 2) and the fingerprint relies on the provider's stable match references; a provider without them re-holds every re-flag until an officer acts.
2. SN-2: the `recorded_at >= completed_at` and sanctions-match-only conditions of `aml_screening_request_resolved` are unreachable through the officer API (the record function refuses the cases that would create them), so they are defence in depth that no test can reach without writing the results table directly. Not mutation-tested.
3. N-4/SN-5: the DB call sites of the environment guard (`policy_set`, `assert_worker_provider`) cannot be exercised on the shared test database (anchored `test`); the helper is tested on scratch databases (unrecorded, production, staging) and the call sites are pinned by a static test.
4. SN-6(b) has two redundant database checks (the check trigger and the guard); the test kills the mutant only when both are disabled.
5. The kyc_verifications guard is narrow: it does not bound `reason`, `reviewed_*` or `submitted_at`.
6. The 7-day window of the parked summary is an engineering value, and `SweepStats.ScreeningParked` (the sweeper-side read of the summary) has no test of its own: the SQL function and the worker-pass counter are tested.
