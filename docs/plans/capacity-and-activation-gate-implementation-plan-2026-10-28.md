## 2. Capacity: what was measured (4 vCPU, 16 GB, PostgreSQL 16.15 default settings, warm cache, synthetic, MOCK provider)
| Finding | Evidence |
|---|---|
| `gate_overdue(5000)` is borderline at ~5 s (4.8-5.3 s) against the 5 s `PhaseTimeout` at 10k persons and saturates at ~5.4-5.7 s from 50k; a tenant above ~5k persons sits at the timeout (9/9 passes timed out on the baseline machine, 3/9 on the reviewer's) | measured, reproduced |
| `enqueue_due` is linear: ~0.17 ms/person (1.7 s at 10k, 8.7 s at 50k, 33 s at 200k): a 200k tenant is never enqueued in a skewed fleet | measured |
| The worker walks tenants serially: ~1.3 s per 1k-person tenant per pass; claims per hour per tenant: 1,440 (1 tenant) -> 1,105 (10) -> 110 (100) -> 24 (500); per-tenant drain is exactly 24 persons/min | measured (500-tenant pass duration extrapolated) |
| `aml_screening_since` grows ~O(V^1.6) with policy versions; with the production call shape (mid-history claim policy) 27.5 ms at V=1000 vs 3.6 ms | measured, reproduced |
| Worker heartbeat is refreshed once per pass but a clear/match finish needs it < 10 min old: a pass over 600 s makes tail finishes fail (AT001), burn attempts and end `failed_terminal`; a real 100-tenant 800 s pass lost 38 finishes in the tail | mechanism confirmed; the 500-tenant pass not run |
| `TenantCap` (500) silently drops tenant #501+ (no log, no metric, no rotation) | confirmed with 501 tenants |
| Payments sweeper RunPass: 0.5 s (one 10k tenant), 4.4 s (10 tenants), 39.6 s (100 tenants) vs a 15 s tick; the 200k-person cycle is therefore a lower bound of 100 min | measured |
| Several workers (production topology = one per API replica on the shared pool): claims/h/tenant scale ~linearly (859 -> 1,753 -> 2,635); no duplicate scheduled requests, provider calls = attempts, no lock waits in 6 runs; CPU 19% -> 56% | measured; the shared-pool gate p95 is 15 ms vs the proposed 10 ms |
| Lost finish with an idempotent-replay provider: every reclaim fails (replayed `screened_at` > 120 s old), attempts climb to `failed_terminal` (fail-closed) | measured (error code inferred) |
| Rolling restart (SIGTERM, 4 claims in flight) burns one attempt and strands 3 claims for ~137 s | measured |
| Retry storm with a shortened 3 s backoff reaches `failed_terminal` at ~410-450 s; default 30 s backoff NOT run | measured (variant) |
| No lock waits or deadlocks in 490 probe windows; cost is per-person plpgsql CPU, not I/O | measured |
Not run: default-backoff storm, a real 500-tenant pass above 600 s, E5 index size/write cost and 200k-probe cost, monitor outputs under the set-based candidate, more than 3 workers, multiple jurisdictions per tenant, alert-row verification for terminal requests, alert delivery. Residual uncertainty: one machine/configuration, uniform data, mock provider.

## 4. Activation-gate design v2.4 in one page
A database-enforced authorisation gate: append-only platform-level evidence tables (authorisations, revocations, attestations, settings, freezes, cut-over inventory, two hash-chain streams), an owner-only lock-row table replacing advisory locks (`screening_gate_locks`; locks only after admission/proof), a last-fired BEFORE INSERT guard on `aml_screening_trigger_policies` that refuses any NEW `gate_withdrawal=true` row without a current, tier-matching, environment/instance-bound, screening-policy-bound authorisation (the gate predicate itself never reads authorisation state; lapse/revoke/mismatch/freeze only block new enabling and alert, never switch a gate off or release a hold), derived classification of existing/legacy/restored gates (cut-over snapshot membership, `legacy_enabling_policy_id`, adoption by governed authorisation), five governed licensing-change kinds (two Persons, officer grants, signed proofs, min approvals pinned at 2), ALWAYS deny triggers + a replica-mode refusal trigger (ORIGIN insert guards), break-glass limited to freeze/revoke with a cap and governed lift, privileged lock watchdog, honest owner/superuser table (detection, not prevention: external verifier with completeness check, manifest compare, DDL audit, pgaudit in Tier N). Migrations: R1 release (100% of instances) -> 0195 evidence/lock/chain/roles/txid -> 0196 kinds -> 0197 lock swap + pair helper (named exceptions to the md5 pin) -> 0198 guard + cut-over (ACCESS EXCLUSIVE first statement; whole-platform maintenance window with API scaled to zero) -> R2. Nothing activates by migration or service start (pinned test).

## 5. Independent review summary
Design: security (6 passes: lock squatting via proof-less definer functions, forced-timestamp classification, replica-mode bypass, role separation, tier binding, configure race: all fixed in the text), database architecture (lock-table CHECK defect, platform-level evidence reads under FORCE RLS, txid default, 0198 lock, 0197 decision tables, `p_locked`/runtime-callable classify functions: fixed), ledger-finance (money safety holds in every lifecycle state; the claim "payout path retries safely during the 0198 stall" corrected: new withdrawal REQUESTS are refused with a misleading 409), QA (about 46 acceptance criteria, mutants M01-M82, fixture plan), operations (monitor, drills, dead-man's switch, Tier S minimum). Benchmark: database performance, operations, ledger-finance (above). Disagreements are listed in section 7 as owner decisions.

## 6. Proposed implementation plan (each stage ends at an approval gate; nothing starts before approval)
**Stage 1 - capacity correctness and observability (Go, tests, runbooks; NO predicate/SQL body change).**
Scope: (a) heartbeat refreshed per tenant/phase so a long pass cannot make finishes fail (ops C1); (b) `TenantCap` truncation made visible (log/metric) and tenant order rotated with a persisted/offset cursor; (c) worker consecutive-failure escalation for the overdue and enqueue phases (like the sweeper's), tenant-tagged log lines; (d) metrics: pass/phase duration, phase timeouts, tenants active vs served, queue depth, oldest-due age, reclaims, finish refusals by code, failed_terminal count, sweeper cycle length; alert rules + a drill proving each fires; (e) rate-limited error logging; (f) re-queue behaviour of `failed_terminal` documented/tested.
Acceptance: pass > 600 s with a hung-provider fleet leaves zero AT001 finish refusals; with 501+ tenants every tenant is served within N passes; each alert fires in a drill; no SQL function body changes (md5 pins); full integration suite, E2E 01-13, hosted CI green; independent security/operations/QA review.
**Stage 2 - capacity SQL (monitors, then enqueue), new function names, shadow compare.** Depends on owner decision D-ORDER. Acceptance: every equivalence case in section 3; differential fuzzing in CI; shadow-compare job raising P1 on any mismatch; measured improvement against the agreed targets (below); ledger-finance sign-off; gate predicate bodies untouched.
**Stage 3 - activation-gate implementation (design v2.4; 0195-0198 + R1/R2).** Depends on OD-M1 (human-provisioned test roles) and D-ORDER. Acceptance: design s15 criteria A-1..A-47 (each with layer, mutants, non-vacuity), mutation run by a non-implementer with survivor list, `amlfix.AuthoriseGate` migration of ~60 fixtures with unchanged assertions, migration matrix (clean, upgrade, down/up, restored DB, mixed versions), V12b monitor cost at 10k persons together with the Stage-1/2 figures, hosted CI on the final code commit, independent security/DB-arch/ledger/QA/operations sign-off. The mechanism stays inert.
**Stage 4 - capacity acceptance report** (template in report appendix A), referenced by the authorisation's `capacity_report_sha256`. Activation remains a separate owner decision.
Proposed targets (PROPOSED; to be set after the owner decisions): T1 every worker database phase p95 <= 1 s at the largest supported tenant (5x headroom on the 5 s timeout); T2 pass time not dependent on fleet size (per-tenant scheduling) or <= interval x k; T3 claims/h/tenant >= the drain objective; T4 sweeper observation cycle <= the gate alert threshold in force; T5 withdrawal gate p95 <= 10 ms with the worker running (production-like shared pool); T6 crash recovery <= lease + the owning tenant's turn (4-12 min at fleet size, not 2.3).
