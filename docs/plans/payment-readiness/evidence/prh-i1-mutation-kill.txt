PRH-I5 finding fix (reported to `payments` by the reconciliation
specialist mid-session, ADR 0095 §4.3 T13 / LF95-C6(a)): T13 second
capture unique-violation
===========================================================================

Bug (as found): a late verified success for a DECLINED attempt whose
SIBLING on the same deposit intent had ALREADY succeeded failed in
ApplyReceiptEvidence with a `payment_attempts_tenant_ledger_tx` unique
violation, because applyDepositSuccessAndPost (receipt.go) linked the
attempt to `updated.LedgerTransactionID` - the INTENT's (i.e. the FIRST
posting's) ledger_transaction_id - instead of the SECOND posting's own
new transaction id. The verified success therefore rolled back and would
have redelivered forever (LF-C1).

Fix: postDepositSuccess (orchestrator.go) no longer short-circuits before
calling ledger.Post when the intent is already 'succeeded'. It always
calls ledger.Post (whose own (tenant_id, provider_id, provider_tx_id)
idempotency naturally collapses an EXACT redelivery to the SAME
transaction id, AlreadyPosted=true), and now returns the transaction id
THIS CALL's own posting produced as a second, explicit return value,
distinct from the (possibly unrelated) intent projection it also returns.
For an intent already 'succeeded' (T13 or an exact redelivery),
deposit_intents' own status/provider_reference/ledger_transaction_id are
left untouched (T13's own row: "the intent's link is left alone if
already set") - every caller (drive.go's applyDepositCallResult,
sweeper.go, receipt.go's applyDepositSuccessAndPost) now links the
ATTEMPT to postDepositSuccess's own returned transaction id, never to
intent.LedgerTransactionID.

New regression test (through the ACTUAL reported code path, not a
hand-built SQL simulation):
    TestReceipt_T13SecondCapture_ThroughApplyReceiptEvidence_LedgerBalanced
    (internal/payments/receipt_integration_test.go) - builds a genuine
    cascade (provider A declines cascadable, provider B's cascade child
    settles pending and then succeeds via its own ApplyReceiptEvidence
    call), then sends a LATE success receipt for the DECLINED PARENT's own
    provider reference through ApplyReceiptEvidence (the exact reported
    shape) and asserts: no error, disposition=applied, the parent moves
    declined->succeeded with its OWN ledger_transaction_id (distinct from
    the sibling's), the intent's own ledger_transaction_id is unchanged
    (still the sibling's first posting), SUM(debits)==SUM(credits)
    (assertLedgerBalanced) and every wallet_balance_projection row still
    reproduces exactly from ledger_entries alone
    (loAssertProjectionMatchesRebuild, the same check
    lockorder_harness_test.go's own projection-vs-rebuild proof uses).
