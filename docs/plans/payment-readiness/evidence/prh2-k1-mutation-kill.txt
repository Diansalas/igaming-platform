MUTANT 7 - killed (RECLASSIFIED from "masked": K1-C3 / code-review F-10)
Predicate: platform co-approval requirement, R-7 (in
           staff_capability_grant_approvals_guard)
Change: removed "IF v_actor.scope <> 'platform' THEN RAISE ... (R-7)".
Original test run: TestCapabilityGrant_A2_TenantScopeApprovalRefused, which
STILL PASSED with the mutant in place at the time mutant 7 was first
attempted, BUT NOT because R-7 is masked - see the correction below: that
earlier write-up mis-analysed why. The implementer's original "masked by
RLS" claim was WRONG (security review K1-C3, code review F-10): PostgreSQL
evaluates a BEFORE INSERT trigger's own RAISE EXCEPTION *before* the
INSERT's row-level-security WITH CHECK is ever tested (RLS's row check runs
against the row's final values, immediately before the heap write - after
every BEFORE ROW trigger has already had its chance to raise). So a
tenant-shaped session's INSERT attempt reaches the trigger FIRST, and the
trigger's own R-7 check is what fires - confirmed empirically: with the
mutant applied, TestCapabilityGrant_A2_TenantScopeApprovalRefused now FAILS
outright (see below), because without R-7 the tenant-shaped INSERT's own
built row then fails RLS's WITH CHECK instead (SQLSTATE 42501, not CG011) -
a DIFFERENT SQLSTATE, which the tightened assertion below catches.
Killers (two, independently pinning R-7 at two different layers):
  1. TestCapabilityGrant_A2_TenantScopeApprovalRefused, now asserting
     exactly CG011 (previously accepted "any error").
  2. TestCapabilityGrant_K1C3_LayeredIndependentKill: inside one owner-role
     transaction that is always rolled back, ADDS a genuinely permissive
     tenant-shaped INSERT policy on staff_capability_grant_approvals (so RLS
     itself could no longer catch anything) and asserts CG011; then ALSO
     drops the decided_by_scope CHECK constraint (so the CHECK backstop is
     gone too) and asserts CG011 again - proving the TRIGGER alone refuses,
     independent of both other layers.
Result: with the mutant applied, BOTH tests FAIL:
  - TestCapabilityGrant_A2_TenantScopeApprovalRefused: "expected exactly
    CG011 ..., got ERROR: new row violates row-level security policy for
    table \"staff_capability_grant_approvals\" (SQLSTATE 42501)".
  - TestCapabilityGrant_K1C3_LayeredIndependentKill: "layer 1 (RLS widened,
    CHECK present): expected CG011, got ERROR: new row for relation
    \"staff_capability_grant_approvals\" violates check constraint
    \"staff_capability_grant_approvals_decided_by_scope_check\"
    (SQLSTATE 23514)".
Both PASS after revert. Byte-identical revert confirmed (md5sum matched the
pre-mutation file). R-7 is therefore an INDEPENDENTLY KILLED control, not
disclosed defense-in-depth riding on RLS or the CHECK - each layer is now
proven to hold on its own.

MUTANT 10 (extra, beyond the required list) - killed (RECLASSIFIED from
"masked": K1-C4 / LF C-K1-1)
Predicate: allow un-revoke / re-revoke, in staff_capability_grants_guard's
           UPDATE branch (`OLD.revoked_at IS NOT NULL` guard).
Change: removed "IF OLD.revoked_at IS NOT NULL THEN RAISE ... 'there is no
        un-revoke'".
The original write-up's "masked" claim covered only the UN-revoke shape (an
UPDATE clearing revoked_at back to NULL), which the separate "an UPDATE must
set revoked_at" check also happens to catch. It did NOT cover the RE-revoke
shape - an UPDATE that keeps revoked_at NOT NULL but supplies a NEW
revoked_at/revoked_by_scope/revoke_reason_code, rewriting the historical
revocation record - and security/ledger-finance both flagged this as a live
gap (K1-C4 / LF C-K1-1): "the implementer's masked claim is wrong" /
"mutant 10 is a live survivor".
Killer: TestCapabilityGrant_A13_AppendOnly, extended with a re-revoke case -
after a genuine revoke, an UPDATE supplying fresh
revoked_at/revoked_by_scope/revoke_reason_code (never clearing revoked_at)
must be refused with CG012 and the row must be read back byte-for-byte
unchanged (revoked_at/revoked_by/revoke_reason_code all compared before and
after).
Result: with the mutant applied, the re-revoke case FAILS ("re-revoke:
expected CG012, got <nil>") - the trigger's whole-row-equality check does
NOT stop a re-revoke, because revoked_at/revoked_by/revoked_by_scope/
revoke_reason_code are exactly the four columns it lets change, and without
the OLD.revoked_at guard the trigger proceeds to unconditionally overwrite
them with fresh actor/now() values, silently rewriting history. PASSES
after revert. Byte-identical revert confirmed. Mutant 10 is therefore an
INDEPENDENTLY KILLED control for the re-revoke shape; the un-revoke shape
remains additionally backed by the separate "must set revoked_at" check
(genuine, disclosed defense-in-depth for THAT narrower shape only).
