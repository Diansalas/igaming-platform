Mutant 10 (a lazy `expired` write on refusal - `UPDATE casino_launch_sessions SET status =
'expired' WHERE id = $1 AND status = 'active'` added immediately before the BootstrapRefusalExpired
return, INSIDE the same transaction, with the same non-nil return the real refusal uses):
EQUIVALENT MUTANT - PASSES, verified empirically rather than assumed:
`PRIV_DB=cas_b_mut bash .../priv_test.sh -tags integration -run TestBootstrapLaunch_ADV_Expired -v
./internal/casino/...` still PASSES with the write physically present in the code. Reason:
BootstrapLaunch runs its entire contract in ONE transaction whose commit/rollback is driven solely
by whether the WithTenant closure returns nil; every refusal returns a non-nil
*BootstrapRefusedError, so pool.WithTenant ALWAYS rolls back the whole transaction - a write
attempted anywhere on a refusal path, PROVIDED the function still returns non-nil, can never survive
to be observed, regardless of whether the write is present in the source. This is a STRONGER
guarantee than the named mutant anticipated (it assumes a ResolveLaunchToken-style architecture
where the lazy write and the caller's own commit/rollback decision are decoupled), not a gap in the
test suite - the mutant was physically introduced, run, confirmed to leave no observable trace, and
reverted (byte-identical diff against the committed original, confirmed via md5sum before and after).

mutant 10, but this variant ALSO changes the function's own return from the refusal error to `nil` -
the only way "the refusal commits" can be true at all under this one-transaction architecture, since
a non-nil return unconditionally rolls back regardless of what was written (mutant 10's own finding).
