Method: each mutant applied directly to the real file, a private database (cas_b_mut, rebuilt from
scratch via priv_db.sh so the mutation was genuinely installed) or the running binary (for Go-code
mutants, just `go build`), the named test(s) run with `-tags integration`, the FAIL captured, then
the file reverted and diffed byte-identical against the committed original before the next mutant.

'TestStoreOutage_DoesNotPinPool|TestResolutionIsolation_' ./internal/casino/...` - green before and

Note on mutants 1-4: every one of provider_id/provider_game_id/asset_code/mode/status/expires_at is
ALSO checked earlier, at step 3 (binding check), which runs first and would refuse a genuine
mismatch before the CAS is ever reached - every one of these session columns is immutable after
insert (migration 0036/0042) and the FOR UPDATE lock held since step 2b prevents any concurrent
change for the transaction's lifetime, so BootstrapLaunch's own ADV tests (which go through step 3)
cannot reach these mutants at all. TestCasConsumeSessionForBootstrap_BindingPredicate/
_RefusesNonActiveAndExpired call casConsumeSessionForBootstrap DIRECTLY, bypassing step 3, to pin
the CAS's own defense-in-depth predicate (ADR 0103 §3.2 step 5/SB-2) specifically.

Mutant 10 (a lazy `expired` write on refusal - `UPDATE casino_launch_sessions SET status =
'expired' WHERE id = $1 AND status = 'active'` added immediately before the BootstrapRefusalExpired
return):
NOT KILLABLE - STRUCTURALLY PREVENTED, verified empirically rather than assumed:
`PRIV_DB=cas_b_mut bash .../priv_test.sh -tags integration -run TestBootstrapLaunch_ADV_Expired -v
./internal/casino/...` still PASSES with the write physically present in the code. Reason:
BootstrapLaunch runs its entire contract in ONE transaction whose commit/rollback is driven solely
by whether the WithTenant closure returns nil; every refusal returns a non-nil
*BootstrapRefusedError, so pool.WithTenant ALWAYS rolls back the whole transaction - a write
attempted anywhere on a refusal path can never survive to be observed, regardless of whether the
write is present in the source. This is a STRONGER guarantee than the named mutant anticipated (it
assumes a ResolveLaunchToken-style architecture where the lazy write and the caller's own commit/
rollback decision are decoupled), not a gap in the test suite - the mutant was physically introduced,
run, confirmed to leave no observable trace, and reverted.

Mutant 11 (revoke on an evaluation error - `RevokeLaunchSession` called immediately before returning
a genuine `bootstrapGateDenialReason` error):
NOT KILLABLE - STRUCTURALLY PREVENTED, same mechanism as mutant 10, verified empirically:
`PRIV_DB=cas_b_mut bash .../priv_test.sh -tags integration -run
TestBootstrapLaunch_EvaluationError_RollsBackNeverDenies -v ./internal/casino/...` still PASSES with
the revoke call physically present - an evaluation error is a non-nil return, so the whole
transaction (including the attempted revoke) rolls back. Session confirmed still 'active' after the
mutated run.

Summary: 10/12 killed; 2/12 (mutants 10 and 11) are structurally unreachable given this
architecture's one-transaction/rollback-on-any-error design - a STRICTLY STRONGER property than the
mutant anticipated, confirmed by physically introducing each mutant and observing zero effect on the
relevant test, not by reasoning alone. No mutant was left in the codebase; every file was diffed
byte-identical against its committed original after each round.
