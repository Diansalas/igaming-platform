commits by an automated runner:
  1. Apply the edit. The runner refuses to apply an edit whose pattern does not match exactly once.
  2. Run the listed tests with `go test -race [-tags=integration] -count=1 -run '^Name$' <pkg>`
     against the local PostgreSQL CI database.
  3. Revert with `git checkout -- <files>` and assert that `git diff` is empty.

"KILLED" means at least one listed test failed. The failure lines shown are the assertion that
failed, taken from the test output. A connection or build failure does not count: the first
automated pass had a runner environment bug (TEST_DATABASE_URL was not expanded), so every
integration result in it was discarded and the whole set was re-run. Those discarded results are
not reported below.

Human requirement: M1 must fail the pool-10 variant of the kept test, which is evidence that the new
call shape is not vacuous. It does. The unrelated-tenant query waited 1.17 s at pool 10, the same
geometry as the original F-POOL-1 measurement of 1.42 s.

Notes on the survivors and the equivalent mutants
-------------------------------------------------

- M14 (casino bet ledger idempotency key made non-stable) SURVIVED
  TestResolutionIsolation_FinancialDuringOutage. The reason:
  - A redelivered bet never reaches ledger.Post. `findPostedBetTransaction` short-circuits
    redelivery on (provider_id, provider_tx_id) first, and the ledger also has the UNIQUE
    (provider_id, provider_tx_id) constraint behind it.
  - So the mutation is equivalent on the redelivery path. It is kept here as a recorded survivor,
    not removed.
  - QA item 4 asked for a mutation that only #7 is shown to kill. That is M14b: the casino webhook
    handler verifies inside the domain transaction again, which is the regression the human's
    "financial requests while the degraded tenant is failing" requirement is about. #7 kills it.
    A pooled transaction stayed open for about 30 s. With pool 10 and 50 blocked A callbacks, each
    held connection waits for a nested read-only acquisition, so B's financial requests starve.

- M15 (healthy owners wait StoreCallTimeout for admission) SURVIVED #3b on the first run.
  - #3b bounded only a failing onset callback, not a slow success.
  - The test was tightened (commit "onset test bounds the healthy caller's latency for either
    outcome"): the callback must finish within SlotWait + 150 ms whatever the outcome, as ADR 0094
    §9.3 3b says.
  - Re-run after the fix: KILLED (H's cold callback took 2.01 s). That run is the one shown above.
    The tightened test then passed 5/5 when run alone.

- M17 (positive-cache key without the tenant; QA item 5's suggestion for #6) SURVIVED
  TestResolutionIsolation_CrossTenant. It is KILLED by TestStoreCache_NoCrossTenantHit.
  - This is an equivalent mutant for #6. Every secret_ref sits in its own tenant's namespace: the
    migration 0096 CHECK, ParseRef, and InNamespace in both registration and the resolver enforce
    that. So two tenants can never share a cache key through the webhook path.
  - The #6 evidence is M5 instead: a breaker keyed by scheme only. #6 kills it at "A's breaker =
    closed, want open".

C8 decision (P = 1 vs the pre-approved P = 2)
---------------------------------------------
- C8-P1 sets MaxConcurrentStoreCallsPerTenant back to the design's 1. It fails
  TestFetcher_ColdStartFourRefs_NoRejection: 2 of 4 cold refs were rejected at 150 ms latency.
- It also fails TestResolutionIsolation_NormalOperation. That failure is its C8 subtest, which runs
  after the main scenario's latency log line shown above.
- The committed value is P = 2, which security pre-approved. SlotWait was not widened.
