# CI run #331 lock contention — investigation, fix, sweep (qa)

Status: **root cause confirmed by live local reproduction; fix applied and verified.** No test skipped, quarantined, retried-to-mask, or given a longer/looser timeout. The task brief's specific SQLSTATE hypothesis (55P03, lock_timeout) is **corrected** by the evidence below — the real mechanism is Postgres's own deadlock detector (SQLSTATE 40P01, `deadlock_timeout`), not a lock_timeout GUC, which does not exist anywhere in this codebase.

## 1. Evidence

- CI run #331 (commit `98a7f08`) failed the "Integration tests" step. The `444e6e1` annotation step named the failing subtest:
  `internal/db TestCatalogueRLS_DeleteAndTruncateAreRefusedLoudly/casino_games_TRUNCATE`, reported duration **1.00s**.
- Run #332 (same code) and three local `-race` replays of `internal/db` alone all passed — consistent with a contention-dependent flake that only manifests when other packages are running concurrently against the same database, exactly as `go test -tags=integration ./...` does in CI (default `GOMAXPROCS`-bounded package-level parallelism, one shared Postgres service container).
- **Grep across the whole repo (`internal/db`, `migrations/`, `deploy/`, `.github/workflows/ci.yml`) for `lock_timeout` finds no occurrence that sets it anywhere** — application code, migrations, CI role-setup steps, and the `TEST_DATABASE_URL`/`TEST_ADMIN_DATABASE_URL`/`TEST_RUNTIME_DATABASE_URL` connection strings. The only two repo hits for the string "lock_timeout" are both comments in `internal/ledger/lockorder_harness_test.go` explaining Postgres's **`deadlock_timeout`** default (1s) — a different GUC entirely.
- Confirmed live against a running `postgres:16.13` instance with this repo's migrations applied:
  ```
  lock_timeout       = 0   (disabled)
  deadlock_timeout    = 1s  (Postgres's own unmodified default)
  statement_timeout   = 0   (disabled)
  ```
  With `lock_timeout = 0`, SQLSTATE 55P03 (`lock_not_available`) is **not reachable** in this environment — a session that blocks on a lock waits indefinitely (until a deadlock is detected or the blocker releases), it never receives a `lock_timeout` error, because none is configured.
- **Live repro** (two psql sessions, one playing the role of "another package's open transaction", the other running the exact code path
  `pool.WithPlatformAdmin(...) { TRUNCATE casino_games CASCADE }`): a two-way lock cycle (TRUNCATE holds ACCESS EXCLUSIVE on `casino_games`, waits on `casino_game_availability`; the other session holds a lock on `casino_game_availability` and, in the same open transaction, later also needs a lock on `casino_games`) reproduces a failure in **1001.581 ms** — matching CI's reported 1.00s to the millisecond — with:
  ```
  ERROR:  deadlock detected
  DETAIL:  Process 12927 waits for AccessExclusiveLock on relation ... ; blocked by process 12928.
  Process 12928 waits for AccessShareLock on relation ...; blocked by process 12927.
  SQLSTATE 40P01
  ```
  Full transcript: `docs/plans/stage-10.3-planning/evidence/ci-331-truncate-lock-repro.txt`.
- `TestCatalogueRLS_DeleteAndTruncateAreRefusedLoudly/casino_games_TRUNCATE`'s own assertion (`assertImmutableViolation`) requires SQLSTATE **P0001** (the deny-truncate trigger's `raise_exception`). SQLSTATE 40P01 fails that assertion cleanly (`expected SQLSTATE P0001 ... got 40P01`) — the trigger never got a chance to fire; a lock conflict aborted the statement first. This is exactly the shape of failure #331 reported.

**Corrected finding vs. the task brief's hypothesis:** the general diagnosis in the task brief — TRUNCATE against a shared-DB table other concurrently-running packages hold locks on, producing an intermittent ~1s failure — **is confirmed**. The specific mechanism named (a 1s `lock_timeout` producing 55P03) **is not** what this codebase does; no `lock_timeout` is configured anywhere. What actually produces a ~1s failure is Postgres's default `deadlock_timeout` (1s, unmodified) detecting a genuine two-way lock cycle and aborting one participant with SQLSTATE 40P01. The fix (isolating the TRUNCATE subtests onto a private scratch database) removes the exposure regardless of which SQLSTATE Postgres would have surfaced, so this correction does not change what needed to be done — only the explanation of why it was needed.

## 2. Root cause (proven)

`TRUNCATE casino_games CASCADE` must acquire ACCESS EXCLUSIVE locks on `casino_games` and every table reachable from it by a foreign key (`casino_game_availability`, `casino_launch_sessions`, `risk_rules`, `casino_provider_rounds`, `casino_catalogue_change_requests`); `TRUNCATE sb_sports CASCADE` has the same shape via `sb_competitions`. CI runs every package's integration tests concurrently against one shared `TEST_DATABASE_URL` database. Stage 10.3 W1c added substantial concurrent test volume against `casino_games`/`casino_game_availability` (internal/casino, internal/httpserver). When another package's test transaction holds a lock on one of the cascade-reachable tables and, within that same open transaction, also later touches `casino_games` itself (a very ordinary shape — e.g. seed-then-verify against both a game row and its availability row in one transaction), a genuine ABBA lock cycle can form with the TRUNCATE transaction. Postgres's deadlock detector (`deadlock_timeout` = 1s, Postgres's own unmodified default — nothing in this repo changes it) resolves the cycle by aborting one side with SQLSTATE 40P01 after almost exactly 1 second. Whichever side is the TRUNCATE test fails the SQLSTATE P0001 assertion. This is inherently timing/scheduling-dependent (which package's test transaction happens to be mid-flight, in which order, at the exact moment the TRUNCATE runs), which is why it reproduced in CI run #331 under real concurrent-package load and not in a single-package local replay or in run #332.

## 3. Fix

`internal/db/catalogue_write_authorization_integration_test.go`:
- The two TRUNCATE subtests (`casino_games TRUNCATE`, `sb_sports TRUNCATE`) were removed from `TestCatalogueRLS_DeleteAndTruncateAreRefusedLoudly` (which still runs its two DELETE subtests against the shared database — DELETE only ever takes a row lock on the identified row plus RowShareLock-class table locks, not an ACCESS EXCLUSIVE table-wide lock, so it does not carry the same exposure).
- A new test, `TestCatalogueRLS_TruncateIsRefusedLoudly`, runs both TRUNCATE subtests against an isolated scratch database created by `internal/testsupport/scratchdb.New` with the **full real migration chain** applied via `Pool.MigrateUp(ctx, "../../migrations")` — the same schema, triggers, and RLS policies as the shared database, just a private instance no other package's test process can ever attach to. `catalogueScratchPool(t)` is the helper (mirrors the existing `sbScratchPool`/`checksumScratchPool` pattern already used elsewhere in this codebase).
- This proves exactly the same invariant (the deny-truncate trigger refuses TRUNCATE loudly, with SQLSTATE P0001, on the real migrated schema) with no retry, no raised `lock_timeout`, and no skip — the exposure is removed structurally, not masked.

Verified: the fixed test passes in ~0.85s even while a separate connection holds `ACCESS EXCLUSIVE` locks on `casino_games` and `casino_game_availability` **on the shared database** for 8 seconds concurrently — proof the fixed test no longer contends for those locks at all (see §5).

**Rule of thumb established by this sweep:** the real exposure is specifically **`TRUNCATE ... CASCADE` (or a multi-table DDL sequence) against a table with FK fan-in from tables other packages hold multi-statement open transactions against**. A plain `TRUNCATE`/single-table `ALTER TABLE` against a table with no incoming FK references cannot cascade to a second table, so at worst it waits (until the other side's short transaction ends) rather than deadlocks — consistent with why only the four CASCADE-across-shared-tables cases above ever showed (or could plausibly show) this failure mode.

## 5. Relation to CI-FLAKE-281

`docs/plans/stage-10.2-planning/02-ci-flake-281-investigation.md` investigated a different, earlier unidentified integration-test failure (run #281). Its own findings:

- The failing test was **never identified** — the job log's last 5,000 lines were entirely the Postgres container's shutdown/checkpoint output, which pushed the actual failing test's output out of the retrievable window.
- §2(c) inspected *that session's own local Postgres server log* (not run #281's actual server log, which was not retrievable) after running the suite against a dedicated database, and found no deadlock/lock-timeout signatures — but this was a normal, unstressed replay, not one that specifically engineered the CASCADE-vs-open-transaction lock-cycle scenario this investigation reproduces above. It does not rule this class in or out for #281.
- §3's local reproduction attempts (`GOMAXPROCS` reduction, `-shuffle=on`, artificial CPU load, a targeted Stage 9 `httpserver` stress run) were aimed at a **different** hypothesis — `internal/httpserver`'s Argon2id-heavy Stage 9 concurrent-auth tests exceeding their fixed 30-second `stage9AwaitAll` wall-clock ceiling under CPU contention — and concluded that was the most likely mechanism. Those attempts did not specifically target `internal/db`'s or `internal/ledger`'s TRUNCATE-under-concurrent-package-load scenario, so this class of failure was never actively tested for in that investigation either.

**Could #281 have been this same class?** Plausible but **not provable either way** from the available evidence:
- *For*: the observed symptom (a Postgres-log-only tail with the real failure detail pushed out) is generic — it would look identical whether the underlying failure was a Stage 9 timeout, a lock-contention deadlock, or something else entirely, since none of those write anything distinctive to that specific truncated tail window. A `deadlock detected` ERROR *would* normally appear in Postgres's own server log at its default `log_min_messages` (`warning`, which includes `ERROR`), so if a deadlock had occurred during #281's run, its own Postgres container log should contain it — but that log line could easily have been earlier in the log than the shutdown sequence that filled the retrievable tail, i.e. exactly the same visibility gap that hid the Go test failure itself.
- *Against*: run #281 predates Stage 10.3 W1c's substantial expansion of concurrent `casino_games`/`casino_game_availability` test traffic (the specific condition this investigation shows is needed to make the `internal/db` case likely) — the CASCADE-fan-in tables implicated here (`casino_games`, `ledger_accounts`, `sportsbook_bets`) existed at #281's time, but the *volume* of concurrent multi-statement transactions against them was materially lower, per this repo's own Stage 10.3 W1c changelog. The CI-FLAKE-281 investigation's Argon2/Stage-9 hypothesis remains independently well-supported by directly measured timing margins (74% of a fixed 30s budget consumed under artificial load, reproducible on demand) that have nothing to do with database locking.
- **Conclusion: no reclassification of CI-FLAKE-281 is warranted from this investigation alone.** Its own registry status (root cause not conclusively proven, classified by strength of evidence, Argon2/Stage-9 timeout assessed most likely) should stand. This document's finding is a *distinct, independently confirmed* root cause for CI run #331 specifically, with its own live reproduction — it does not supersede or explain away #281's own analysis, which explicitly reasoned about a different code path.

## 6. Disposition recommendation for the registry

- Register a new entry (e.g. `CI-FLAKE-331` or fold into the existing lock-contention thread if the registry already tracks one) with status **root cause confirmed by live reproduction, fix applied and verified** — this is stronger evidence than CI-FLAKE-281's "classified by strength of evidence, not conclusively proven," and should not be conflated with it in the registry's confidence language.
- Record the fix (§3) and the sweep (§4) as complete; no follow-up action needed for the "no fix" rows in §4 unless Stage 10.3 or later work adds a `CASCADE`-capable TRUNCATE/DDL test against one of those single-table targets that *also* gains incoming FK references from a newly-shared table — at that point the same rule of thumb (§4) applies and the same fix pattern should be used pre-emptively, per how `internal/ledger` and `internal/sportsbook` were treated in this pass.
- Correct the record for what "confirmed" versus "inferred" means here: the **general exposure class** (shared-DB CASCADE TRUNCATE racing concurrent packages) is proven by direct reproduction (§1); the **specific claim that CI-FLAKE-281 was the same mechanism** is inferred/plausible only, explicitly not proven, and should not be asserted as fact in the registry.
- CI-FLAKE-281 itself should remain open under its existing classification (devops+qa, Argon2/Stage-9 timeout most likely) — this document does not close it.
