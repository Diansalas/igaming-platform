## 1. Executive summary

1. The "player-scoped jurisdiction resolver" is, today, a closed circuit that never resolves. `jurisdiction.Resolve` returns `unresolved(no_signal)` for every player-scoped call (`internal/jurisdiction/resolver.go:61-71`, test `TestResolve_PlayerScopedOperationAlwaysUnresolvedNoSignal`, ran, passes). `DeterminePlayerJurisdiction` (precedence.go:100) has zero production callers (grep over `internal/` and `cmd/`: only tests). `RequiredPurposes` is an all-undetermined table (`operation_purpose.go:62-67`, HDR-J-7). `jurisdiction.Persist` and `jurisdiction.IsActive` also have no production caller.
2. Because of that, every control keyed to the resolver is either NOT ARMED (silently allows) or ARMED (denies every player, blocked or not). There is no working middle state: casino game blocklist (`casino/orchestrator.go:967-986`), sportsbook restrictions (`sportsbook/jurisdiction.go:176-190`), jurisdiction-scoped risk rules (`risk/evaluator.go:91-109`), and bonus (all checkpoints denied by AssetAuthorization with a zero jurisdiction, `bonus/eligibility.go:84`, `assetregistry/authorization.go:83`).
3. What actually protects players and licences today is NOT the resolver. It is three other mechanisms, all real and fail closed: (a) `marketgate` (operating-market gate: licence validity, licence country ceiling, tenant/brand/operation rungs, evidence = country of the player's KYC-verified residence), applied at registration (brand-level only), deposit initiation, casino launch, casino new bet (brand-level only), launch-token bootstrap and sportsbook placement; (b) tenant/brand status gates (ADR 0112) on deposit, withdrawal, payout, bet and registration; (c) licensing-jurisdiction rulebook selection (`tenants.licence_id -> licences.jurisdiction_id`) for KYC thresholds, RG floors and AML screening policy.
4. Biggest default-allow holes: AML sanctions/PEP screening has no automatic trigger anywhere (registration, KYC approval, schedule) and transaction monitoring does not exist; KYC enforcement is dormant (`not_required`) with no policy row and with no licence bound; RG limit enforcement is OFF by default per tenant/brand and launch readiness does not force it on; `LaunchGame` has no tenant/brand status gate (only bets do); a `deposit` risk rule can be authored but is never evaluated.
5. "One brand, one licence, one jurisdiction (Anjouan)" can be made safe by configuration alone (section 5). A second jurisdiction cannot be served correctly by one tenant: a brand has no licence of its own, so a second jurisdiction means a second tenant with its own licence. Per-player jurisdiction (rules chosen by where the player lives) needs human decisions HDR-J-7 (purpose mapping), PC-GAP-1/2 (location policy) and a country-to-jurisdiction mapping that is not designed anywhere (section 6).

- The licensing jurisdiction is deliberately NOT fed into player-scoped resolution. The two vocabularies are never bridged anywhere (`jurisdictions.country_code` exists, `SetJurisdictionCountryCode` registry_admin.go:172, but ADR 0045 INV-M-4 forbids reading it for market decisions, and no code reads it at all).

## 4. Every place an unresolved jurisdiction or missing configuration becomes "rule not evaluated" or default allow

Each of these is a way a rule that an operator believes is in force is silently not applied.

1. Casino game with empty `jurisdiction_blocklist`: control not armed, allows regardless of resolution (K3-1, `casino/orchestrator.go:967-970`; test `TestLaunchGame_EmptyBlocklist_NonRegression`). Same for sportsbook with no restriction rows (`sportsbook/jurisdiction.go:176-179`). Designed (K3-1); consequence: a blocklist entry "MT" does not mean "players in MT are blocked", it means "all players are blocked".
2. `risk.OperationDeposit` is a valid operation for rule authoring (`httpserver/risk_handlers.go:175`, `risk/types.go:111,138`) but no deposit code path calls `risk.Evaluate` (production callers: casino launch/bet, sportsbook, bonus, withdrawal only). A deposit limit or jurisdiction/licensing-mode rule is accepted, stored, and NEVER evaluated. The comment at `risk/types.go:97-100` ("only casino launch and bet are enforced") is stale. Silent not-evaluated.
3. Jurisdiction-scoped risk rule: not "not evaluated" but over-blocking. Casino launch and bet pass `""`, so creating one makes `ErrMissingJurisdiction` abort every launch/bet of that tenant (or of all tenants if platform-wide); the withdrawal gate never passes a jurisdiction at all, so such a rule on `withdrawal` would refuse every withdrawal and dispatch (player funds stuck). `jurisdiction.IsActive` (the designed R-2b precondition for `risk.CreateRule`) has no production caller (`jurisdiction/resolution_active.go:123`), so nothing stops authoring it (`risk_handlers.go:244`).
4. KYC enforcement for deposit and play: tenant with no licence bound returns `not_required` (`kyc/enforcement.go:262-267,274-279`; test `TestHold_EvaluatedEvenWhenKYCIsNotRequired` comment, `financial_flow_integration_test.go:224`). With a licence but no active `kyc_enforcement_policies` row it is dormant `not_required` (`enforcement.go:742-749`; migration 0100 seeds zero rows). `edd_amount` and `registration_tier` trigger types are modelled and never consulted (`enforcement.go:27-38`, "KNOWN GAP"). Withdrawal is the only operation with an unconditional structural KYC rule. Note the market gate independently forces an approved KYC with a recorded residence before deposit, launch and sportsbook, so first-money KYC is enforced indirectly even when the KYC policy table is empty; casino bets after launch are not re-gated by it.
5. RG limit enforcement is OFF unless `rg_enforcement_activations` has a row (`rg/enforcement.go:147-167`); there is no way back off. With it off no deposit/loss/wager limit and no mandatory-limit rule is applied, and `rg_config_missing` is never raised. Launch readiness `R-RG-CONFIG` is informational (ADR 0112 section 2.6), so a brand can be activated with limits not enforced.
6. RG compose with a tenant that has no licence (`jur == nil`): returns "no configuration" (`rg/limits_service.go:318-320`): players can set limits without a ceiling; if enforcement is ON this instead refuses everything (`rg_config_missing`).
7. AML: no automatic sanctions/PEP screening at registration, KYC approval, deposit, withdrawal or on a schedule (orchestrator has no production caller); transaction monitoring does not exist (`R-AML-MONITORING` "always fails, explicitly", `a7-aml-record.md` row 3). Only manual holds are enforced.
8. Per-bet country for casino: not evaluated after launch; bounded only by the 4 h session lifetime and the brand-level market-open check (`casino/market_exposure.go:11-29`, PROVIDER DEPENDENT residual, recorded).
9. Registration: no player country at all (brand-level rule). Recorded owner-reversible product decision PD-MKT-REG-1.
10. `licences.permitted_products` and `permitted_markets` (migration 0002:23-24): stored and returned by the admin API, never read by any enforcement path (grep over `internal/`: only `registry_admin.go` and the HTTP handler). Licence PRODUCT scope is therefore not enforced; product availability is controlled solely by operating-market operation/product rungs being opted in. DB-FIELD-ONLY.
11. `tenant_jurisdiction_configs.kyc_ruleset_id / aml_ruleset_id / rg_ruleset_id / reporting_ruleset_id / allowed_payment_methods / geo_block_list / allowed_currencies`: read only by launch readiness (`launchgov/readiness.go:200,830`, `hard.go:228`). ADR 0006 and `docs/architecture/15-*` state compliance rulesets and payment methods are resolved from it at runtime; that is DOC-ONLY. DB-FIELD-ONLY for enforcement.
12. Withdrawal approval does no status, licence or AML re-check (gates at request and dispatch). Acceptable by design, but a licence suspended between request and dispatch does not stop the payout (no licence check at dispatch).
13. Licence validity is never evaluated for withdrawal, payout, KYC, AML, RG, bonus or login (only `operatingmarket` and `launchgov` call `EvaluateLicenceValidity`). Whether payouts should continue while a licence is suspended is a policy question that the repo does not record.
14. `jurisdiction.Persist` (the append-only resolution record) has no production caller, so no per-decision jurisdiction record exists; the sportsbook bet and casino session store an empty jurisdiction.
15. Launch authorisation does not require licence validity or an open market: readiness is informational and only H-1/H-2/H-3/H-6 refuse (ADR 0112 sections 2.6, 2.7; `launchgov/hard.go:1-10`). A brand can be activated with an expired licence; at runtime the market gate then refuses deposit, launch, bet and registration, but withdrawals continue.

## 5. Safe configuration per brand

### 5.1 First brand: one licence, one jurisdiction (Anjouan)

Required, in this order, none of which the platform does for you (`seed-market` is the only writer of market rows: no HTTP route, no Back Office; `cmd/seed-market/main.go`, `stagingseed/market.go:232,272`):

1. Tenant `licensing_model = under_platform_licence`; `PUT /v1/admin/tenants/{tenantID}/licence` binds an `active`, date-valid platform licence (`jurisdiction_admin_routes.go:76`, DB FK `tenants_licence_matches_model` migration 0007). API-ONLY.
2. Operating-market rows (all four rungs must exist or everything refuses, ADR 0045 INV-M-2): `licence_country_ceilings` (enabled, per country), tenant rung per country, optionally brand and operation/product rungs (casino, sportsbook opt-in). Seeded by CLI/SQL only.
3. `jurisdiction_evidence_collection_active(verified_residence)` ON for the tenant (`PUT /v1/admin/jurisdiction-evidence-collection/{evidenceType}`), otherwise a reviewer cannot record residence and no player can ever deposit or launch.
4. Brand and tenant launch authorisation (ADR 0112 four-eyes) to move `pending_launch -> active`. `R-LIC-VALID`, `R-MARKET-CONFIG`, `R-RG-CONFIG`, `R-AML-*` are informational and must be acknowledged, not passed.
5. RG: platform-approved floors for the licence jurisdiction (floor change-request flow, `rg_limits_routes.go:99-105`), then `POST /v1/admin/rg/enforcement` (step-up critical) to turn limit enforcement ON for the brand. Without step 5, no limit is enforced.
6. KYC: author `kyc_enforcement_policies` for the Anjouan licensing jurisdiction (cumulative_deposit per asset, play per operation). Without it KYC is only the market-residence precondition plus the structural withdrawal rule. Note an asset not covered by an existing deposit policy is `unavailable` (refuse), by design.
7. Keep `geolocation/locator` = `KYCResidenceLocator`; the static MOCK locator is refused in production (`marketgate/kycresidence.go:70-76`, `TestEveryProductionCallerOf...`, ran).
8. DO NOT author: jurisdiction-scoped risk rules (any operation: bricks launch/bet/withdrawal, G6), `deposit` risk rules (never evaluated, G7), casino `jurisdiction_blocklist` entries or sportsbook restrictions unless the intent is "disable for everyone". Bonus stays blocked (no player jurisdiction), which is the intended fail-closed state for a first launch.
9. AML: manual only. Provision the officer quorum (`R-AML-QUORUM`), accept that no automatic sanctions screening or monitoring exists, and gate go-live on that decision (G2).

### 5.2 Second jurisdiction

- Same tenant, second jurisdiction: NOT supported for rulebooks. A brand carries no licence (`migrations/0008`; architecture doc 15 "a brand has no independent operating jurisdiction", RULING BI-4I-1). KYC, RG, AML policy are keyed to the tenant licence's single jurisdiction. Players resident elsewhere are only filtered by country ceilings and rungs, not by different rules.
- Second jurisdiction as a second tenant with its own licence: SUPPORTED by the existing model. `own_licence` tenants get an exclusive licence (`uq_tenants_exclusive_own_licence`, tests `TestQAAdversarial_UniqueOwnLicenceIndex...`); platform-licensed tenants share the platform licence. Each tenant needs its own steps 1-9 above, its own floors and KYC policies for its licence jurisdiction. Everything is configuration (`TestReceiveCallback_SecondJurisdictionIsConfigurationOnly`, casino, not run by me).
- Rules chosen by where the PLAYER lives (not where the operator is licensed): NOT SUPPORTED, needs section 6 plus decisions.

## 6. Minimum provider-independent wiring for real per-player jurisdiction resolution (without inventing legal rules)

Separate the two problems the code currently blurs.

### 6.1 Operator-side ("licensing") jurisdiction: already de facto brand -> tenant -> licence -> jurisdiction

This is not player resolution and HDR-J-1 does not forbid it (ADR 0096 and 0115 use it for rulebooks). What is missing is that it is an implicit join duplicated four times (`kyc/enforcement.go:435`, `rg/limits_service.go:270`, `launchgov/hard.go:183`, AML via caller-supplied `JurisdictionID`) with different no-licence semantics (KYC `not_required`, RG "no config", launchgov hard failure, AML requires id). Minimal fix: one shared read-only helper `jurisdiction.ResolveLicensing(ctx, q, tenantID) -> {jurisdictionID, code, licenceID, validity, basisKind}` returning an explicit tri-state (bound / explicitly-not-applicable per recorded ADR 0112 determination / unbound), used by all four, with the explicit-not-applicable state read from the recorded launch licensing record rather than from an absent licence. This is explicit brand -> licence -> jurisdiction wiring, human-approved at activation time by the existing ADR 0112 four-eyes record. No legal rule invented. The existing `tenants.licence_id` assignment is already platform-admin only with audit (`tenant_licence_admin.go`).

### 6.2 Player-side jurisdiction

What exists and is sufficient without any vendor: `kyc.ReadMarketResidenceEvidence` (verified residence, production-eligible), `identity.GetDeclaredResidence` (self-declared, gated by `jurisdiction_evidence_collection_active`), `DeterminePlayerJurisdiction` (pure, `PurposeIdentityDetermination` needs NO location policy, `precedence.go:94-106`).

Minimum wiring, each step small and independently reviewable:

1. A composition-layer adapter (same position as `marketgate`: it may import identity, kyc and jurisdiction; `jurisdiction` may not) that builds an `EvidenceSet` from the two accessors with the correct `ok` semantics (absent vs empty) and calls `DeterminePlayerJurisdiction(PurposeIdentityDetermination)`. Verified residence wins over declared; location is never a substitute (already tested: `TestDetermine_VerifiedResidenceIsAuthoritativeForIdentityDetermination`, `TestDetermine_LocationSignalIsNeverASubstituteForVerifiedResidence`). The result is a COUNTRY (evidence-derived), not a jurisdiction row.
2. Persist the decision with `jurisdiction.Persist` (exists, no caller) so each decision has a record; this also gives the missing audit trail.
3. Make `jurisdiction.Resolve` consume the adapter result for player-scoped classes with a new reason/basis (the type system already forbids `tenant_licence` and `platform_fallback`; the CHECK at migration 0071:73 remains). Keep `unresolved` when evidence is absent.
4. A country-to-jurisdiction mapping so a country can be compared with `jurisdictions.code` entries used by casino blocklists, sportsbook restrictions and risk rules (`sb_jurisdiction_restrictions.jurisdiction_code REFERENCES jurisdictions(code)`, migration 0087:55). This mapping is the one part that cannot be done without a human decision (see section 7). Provider-independent options: (i) make catalogue-level blocklists and restrictions country-keyed (ISO alpha-2, the vocabulary `marketgate` already uses and validates) and stop pretending they are jurisdiction codes; (ii) or add an explicit, human-approved, versioned `country -> jurisdiction` table. Do not derive it from `jurisdictions.country_code` without recording the decision (ADR 0045 INV-M-4).
5. `RequiredPurposes` table content (HDR-J-7): one-line literal per operation class once the owner answers. Until then keep it failing closed.
6. Only then add the R-2b precondition (`jurisdiction.IsActive`) to `risk.CreateRule`, so jurisdiction-scoped rules can only be authored once resolution is actually active for that tenant and class.

Nothing in 1-3 or 5-6 needs a vendor. Location (`LocationSignal`) stays out: PC-GAP-1/2 policy is unset and `ErrPolicyUnset` is the designed outcome for market-access purpose.

Note for step 4(i): the existing `marketgate` already provides per-operation, per-brand, per-country blocking from verified residence. For "block this one game/event in country X", extending that same evidence to the catalogue controls is the smallest change and invents no legal rule; for "apply a different rulebook because the player lives in country X" there is no minimal safe shortcut.

## 8. Hybrid-model enforcement (`under_platform_licence` vs `own_licence`)

Where behaviour differs by `tenants.licensing_model` (all verified in code):

- Schema: `tenants_licence_matches_model` composite FK couples the model to `licences.licensee` (platform vs tenant), and a unique index gives an `own_licence` licence to exactly one tenant (`uq_tenants_exclusive_own_licence`, `tenant_licence_admin.go:142-150`). IMPLEMENTED-VERIFIED (qa adversarial registry tests).
- Risk: `RiskRequest.LicensingMode` is resolved from the tenant row and rules may be scoped by it (`risk/evaluator.go:186,234`; callers casino, sportsbook, bonus, withdrawal gate). A missing mode with a scoped rule fails closed (`TestEvaluate_MissingLicensingModeFailsClosed`). Not evaluated for deposit (G7).
- Launch governance: hard precondition H-2 checks model, licensee and binding consistency (`launchgov/hard.go:150-215`).
- Credentials: ADR 0006 says credential ownership follows the model; no `licensing_model` read exists in `providercred` or payments outbound resolver (grep), so any model-specific credential behaviour is by per-tenant credential rows, not by the model. I could not confirm model-specific credential enforcement.

Where behaviour does NOT differ (gaps for the hybrid design):

- AML: officer scope is chosen from the token (tenant vs platform), never from the licensing model. A platform token acts as `platform_acting` in any tenant including `own_licence` ones (`aml_routes.go:135`, `canActOnTenant` `admin_routes.go:27-29`). Same for governed manual adjustments and withdrawal-hold resolution (`platform_acting` scope).
- RG floors: always keyed to the licence jurisdiction and approved by platform staff (`requirePlatformToken`, `rg_limits_routes.go:99-105`) regardless of whose licence it is; no own-licence tenant can approve its own jurisdiction floor and nothing distinguishes the cases.
- KYC thresholds and AML screening policy: keyed to licence jurisdiction only; same code path for both models.
- Reporting: `reporting_ruleset_id` is never read; no per-model or per-jurisdiction report format exists. SAR export NOT IMPLEMENTED (`a7-aml-record.md`).
- Licence validity: same for both models; no check that a `tenant`-licensee licence belongs to the tenant after binding other than the FK.
- Payments/credentials by model: see above.

Back Office coverage for the regulated-configuration APIs (grep of `backoffice/src`): launch authorisation UI exists and lists licences/jurisdictions read-only (`api/launch.ts`); tenant creation chooses `licensing_model`; AML queue exists (`features/aml`). API-ONLY (no Back Office path found): licence assignment to tenant, jurisdiction/licence creation, `jurisdiction-resolution-active`, `jurisdiction-evidence-collection`, RG enforcement activation and limit configs, risk rules, sportsbook jurisdiction restrictions. NOT IMPLEMENTED anywhere (no API, no UI): operating-country policies and licence country ceilings (CLI only), licence status transitions (suspend/expire: no code path updates `licences.status`; only SQL or the `expires_at` date), country-to-jurisdiction mapping.
