(LOCAL, private scratch databases, runtime role). Baseline c5b30c7; branch gov-r16-hsec. 2026-10-08.
Status of the feature: IMPLEMENTED against MOCK (no provider is involved, called or needed).

Method. Each mutant is applied IN PLACE to ONE production file (original backed up first); for a Go mutant the touched
package is compiled (`go vet -tags integration`; a mutant that does not compile is reported INVALID and NOT counted -
there were none); then ONE targeted pattern runs with `go test -tags integration -count=1 -p 1 -run <pattern> <pkg>`
against the private DB. KILLED = at least one test fails. The original is restored after every mutant and compared
with `cmp` against the backup. SQL mutants are applied to the migration file migrations/0124_..._up.sql IN PLACE: every
integration test builds its OWN scratch database by migrating that file, so a SQL mutant only ever reaches scratch
databases (the private DB hsec_r16_probe is never mutated). Script: scratchpad hsec_mut/mut.py + mutants.py (not
committed). Control: before the first mutant of each pattern the UNMUTATED tree runs the same pattern - every control
PASSED (a failing control would have voided its mutants). The patterns are the test names listed per mutant.

Round-1 survivors that were REAL test gaps, fixed and re-run:
- S01: the beneficiary guard (fires first) also refuses a non-acting scope, masking the resolution guard's own check.
  Test strengthened: TenantStaffDenied lifts the beneficiary guard for one statement and requires HR001 from the resolution
  guard itself.                                                                                         r2: S01 KILLED.
- S08: a raw UPDATE of a payload column without a state change hit the "invalid transition pending -> pending" branch, so
  the immutable-column list was never the deciding check. Test strengthened: the same column changes ALONGSIDE a legal
  state change (state='cancelled', requested_by / evidence / reason changed) must be HR030.             r3: S08 KILLED.
- S33: the acting entries fence repeats the correlation binding, so the wrong-correlation attack through ledger.Post was
  refused either way. Test strengthened: a header-only raw INSERT into ledger_transactions (no entries) with a wrong
  correlation, with each header layer lifted in turn (key guard alone -> HR020; acting fence alone -> CG030). r2: S33 KILLED.
- G07 (hang): the failing assertion left the executor parked on the test hook, holding its connection, so the pool Close
  hung until the 25 min timeout. The concurrency tests now release the hook on every exit path (sync.Once).  r2: G07 KILLED.
- G13: no test raced a grant revocation against an execution. New hook testHookHoldResolutionAfterShareLocks and test
  Concurrency_ExecuteVsGrantRevocation (the revocation must WAIT for the release to commit).               r3: G13 KILLED.

Honest survivors (5: S09, S45, S46, S47, G12), each with the reason it cannot be killed by a behavioural test:
- S09 payload_hash recomputation check: payload_hash is itself in the immutable-column comparison that runs first, so a
  forged hash is refused as an immutable-column change; the recomputation is defence in depth.
- S45 proof trigger "only the requester may cancel": the base resolution guard fires first and refuses a non-requester
  cancel (HR030); the proof trigger repeats it.
- S46 counting filter decided_by_scope = 'platform_acting': an approval row of any other scope cannot exist (column CHECK
  + approvals guard + no tenant RLS policy); the filter is belt and braces.
- S47 partial UNIQUE (one executed per withdrawal): a second execution is already impossible (the withdrawal leaves
  `approved`, the L1 lock serialises, the state CAS and the governed-key idempotency); the index is the last line.
- G12 request-time L1 lock via LockForPayoutEvidence: a plain read still blocks behind a concurrent FOR UPDATE because the
  FK check of the child INSERT takes FOR KEY SHARE on the withdrawal row. The lock call fixes the LOCK ORDER (L1 before
  the tenant advisory lock) which no test can observe without a deadlock-prone ordering harness. (Test
  Request_TakesTheWithdrawalL1Lock pins the waiting behaviour; it passes with either implementation.)
