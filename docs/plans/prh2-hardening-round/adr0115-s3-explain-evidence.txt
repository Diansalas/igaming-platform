for the target player over 400 days (1,751 of them in the last 30 days, 598 in the last 7 days, 300 in the last 24 h), 40,000 +

WHAT THIS IS NOT: it does not measure the casino bet / sportsbook place / deposit T1 request paths. S3 wires nothing, so the p95 DELTA
on those three paths named in ADR 0115 3.4 cannot be produced yet (label BLOCKED on S4 wiring). The numbers below are the cost S4 adds
to each of them (the usage reads) on this dataset; the end-to-end delta must be re-measured when S4 is wired. No SLA is claimed.
Timings include the round trip to a local PostgreSQL and come from one run on a shared machine.

READING THE NUMBERS. Stake usage p95 is about 87 ms and the L0.4 lock is held about 108 ms (p95) by the two reads together for a
Person with about 5,000 ledger rows in the 30-day window. The cost is proportional to the rows of the LONGEST window the statement
reads (the design of 3.4: one scan, every window by FILTER), not to the player's history: the contrast plan below, without the 0135
index (legacy index idx_ledger_entries_account, 15,498 index entries visited instead of 4,750 rows), shows the same statement taking 109 ms
instead of 58 ms on this dataset (EXPLAIN ANALYZE execution time, single run). A very high-volume Person (hundreds of thousands of
entries per 30 days) would pay proportionally more under the lock; the ledger-derived rollup named in 1.4 is the recorded answer and is
NOT built. This is a decision input for S4, not a defect claim.

Seeding the ledger through the real triggers dominated the 13 minute run (the balance-projection trigger updates one row per entry;
batches of 250 transactions keep that roughly linear; the machine was shared).
