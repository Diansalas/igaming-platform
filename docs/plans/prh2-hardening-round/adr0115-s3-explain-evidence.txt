CORRECTION (ledger-finance F-i). The first evidence run seeded NO ledger deposit rows, so its deposit plan and its deposit-usage
timings (p95 26 ms) were not representative. This run seeds 5,075 deposits for the target player and 40,000 for another account
of the tenant (ANALYZEd); with them the deposit read is p50 37 ms / p95 52 ms and its plan still uses
idx_ledger_entries_tenant_player_asset_created and idx_deposit_intents_tenant_player_asset_created with no sequential scan of
ledger_entries or deposit_intents (asserted by the test).

Produced by: RG_S3_SCALE=large go test -tags integration -p 1 -count=1 -run TestRGUsageS3ExplainAndLatency -v ./internal/rg
(PRIV_DB harness, PostgreSQL 16, one shared development machine that other sessions were also using). Dataset: 20,300 casino bets
for the target player over 400 days (1,751 of them in the last 30 days, 598 in the last 7 days, 300 in the last 24 h), 40,000 +
40,000 bets for two other accounts of the tenant (the second is the target's Person), the deposits above, 8,000 + 40,000 deposit
intents, 290,600 ledger_entries rows in total, ANALYZEd. The measurements are of the usage statements themselves, run as the
RUNTIME role in tenant staff scope (RLS active), inside a transaction holding the L0.4 person advisory lock. The Person scope
(target + its second account) with four windows (24 h, 7 d, 30 d, Berlin calendar day) is the heaviest shape.

WHAT THIS IS NOT: it does not measure the casino bet / sportsbook place / deposit T1 request paths. S3 wires nothing, so the p95
DELTA on those three paths named in ADR 0115 3.4 cannot be produced yet (label BLOCKED on S4 wiring). The numbers below are the
cost S4 adds to each of them (the usage reads) on this dataset; the end-to-end delta must be re-measured when S4 is wired. No SLA
is claimed. Timings include the round trip to a local PostgreSQL and come from one run on a shared machine.

READING THE NUMBERS. Stake usage p95 is about 85 ms; both reads together hold the L0.4 lock about 132 ms (p95) for a Person with
about 5,000 ledger rows in the 30-day window. The cost is proportional to the rows of the LONGEST window the statement reads (the
design of 3.4: one scan, every window by FILTER), not to the player's history. A heavy player (300,000 or more bet+win rows in 30
days) costs about 13 microseconds per row, i.e. 100,000 bets is about 1.3 s p50 (ledger-finance's measurement): S4 must measure that
case, add a statement_timeout and decide on the ledger-derived rollup BEFORE enforcing 30-day or calendar-month wager/loss windows
on the casino path. The contrast plan below (same stake statement without the 0135 index, in a rolled-back transaction) is NOT a clear win for the new index on this dataset: one EXPLAIN run each gave 109.6 ms with the index and 85.9 ms without (the first run of this evidence gave 57.7 ms and 109 ms the other way round); single runs on a shared machine are noise at this scale, and the legacy idx_ledger_entries_account also serves a tenant this small. What the test asserts is structural (the new index is used, no sequential scans); the index's value is for a large multi-tenant table, which this dataset does not reproduce. A decision input
for S4, not a defect claim.

Seeding the ledger through the real triggers dominated the 7 minute run (batches of 250 transactions keep it roughly linear).
