Method. Each mutant is applied IN PLACE to one production file (original backed up first), the touched packages are
compiled (`go vet -tags integration`; a mutant that does not compile is reported as COMPILE-ERROR and NOT counted), then
`go test -tags integration -count=1 -p 1 -failfast -run TestHSEC <pkgs>` runs against the private DB. KILLED = at least one
test fails. The original is restored after every mutant. Script: scratchpad r13a_mut.py (not committed).

final report). Restore check: after the whole sweep `git status --short` is empty and `cmp backup file` is identical for

Honest survivors (2):
S1 M03 (call-site fail-open on a read error in deposit phase A) - EQUIVALENT BY TRANSACTION ABORT, not killed by a test. In PostgreSQL
   any statement error aborts the transaction, so a swallowed gate read error is followed by the intent insert failing with
   "current transaction is aborted"; nothing is created and the request still errors (500, not 409). The helper itself is
   pinned fail-closed by M17/M18/M19/M20. Reasoned, not test-proven at the call site.
S2 M23 (brand SELECT without `AND tenant_id = $2`) - EQUIVALENT UNDER THE RUNTIME ROLE. `FOR SHARE` applies the brands UPDATE policy
   (tenant-scoped), so another tenant's brand row is filtered out of a locking read even without the predicate; the explicit predicate
   is defence in depth (and the composite FK (brand_id, tenant_id) on deposit_intents / withdrawal_requests would also refuse).
   TestHSEC5_Deposit_BrandOfOtherTenantOrMissing_Refused passes with and without it. Not killable without a superuser/BYPASSRLS
   connection, which this project forbids.

Not mutated (and why): "check before lock" for deposit (the gate IS the first statement; nothing is locked before it) and "check
after the insert" (equivalent: the refusing transaction rolls back whole; the replay variant M04/M28 is the observable one).
Other-tenant isolation is asserted by TestHSEC5_Deposit_OtherTenantUnaffected, TestHSEC11_RequestWithdrawal_OtherTenantUnaffected and
TestHSEC11_ClaimForDispatch_OtherTenantUnaffected (no mutant isolates it separately: the helper is keyed on the caller's ids).
