# Nuvei verified documentation matrix (PSP phase 1B, documentation-only)

Status: READ-ONLY DOCUMENTATION VERIFICATION. No code, no sign-up, no credentials, no network calls other than WebFetch of official pages. Date of reading: 2026-10-19. Platform frozen at `1505a165e9152729b5df573211c80b1c0a35bc87`; branch `nuveidoc`, based on `claude/focused-wright-jw88w9`.

Evidence caveat (read this first). WebFetch converts the page and answers through a small model. Quotes below are the fragments that tool returned and are kept to <= 125 characters; every security-critical item (DMN checksum, REST 2.0 webhook signature, status queries, payout inputs) was fetched at least twice with different prompts, and where the second read adds precision it is stated. No page showed a "last updated" date other than the release-notes page. Where WebFetch itself flagged an internal inconsistency in the vendor page, it is recorded as a vendor inconsistency. "NOT VERIFIED" means the page was fetched and does not state it, or could not be fetched.

Three Nuvei API surfaces appear in the docs and they are NOT interchangeable. Every row names which one applies:

- LEGACY = REST API 1.0 (`/ppp/api/v1/*.do`, `checksum` request signing, DMN webhooks). No deprecation notice found (release notes 20 Aug to 13 Oct 2026 checked).
- REST2 = REST API 2.0 (`https://api.nuvei.com/payment-api/...`, `x-api-key`). Every page and the release notes label it "Beta Release"; no GA or end-of-beta date.
- CP-EVENT = Control Panel "Event DMNs" (chargebacks, pre-chargeback alerts, manual corrections): a separate JSON webhook family with its own checksum.

## 3. Resolution of findings

Recommendation of the readings (a verification result, not a design decision): REST2 closes G-01, N-1 and KT2 cleanly for payments but is Beta and has no documented settlement report or read-only key; LEGACY is stable (no deprecation notice) but needs a status-query bind and a body-field extension. The payout family is the weakest in both generations.

### G-01 signature location vs header-only `Extract`
- L payment DMN: the checksum is a body parameter `advanceResponseChecksum` (also `responseChecksum`), not a header. The page never states whether it is query string, form body or JSON, nor the HTTP method ("Not stated on the page: HTTP method, content type, character encoding of the request body"). Examples are URL-encoded key=value strings with `+` for spaces.
- L withdrawal DMN: `checksum` is a listed parameter of the DMN ("The checksum of the request. This checksum should include all the parameters of the request and your secret key."); location (query/body/header) "not stated".
- CP-EVENT: "Event DMNs include a `checksum` in the header" (the only header-borne checksum in L; the Control Panel page names it `checksum`).
- R2 webhook: headers `X-Authentication-Timestamp` and `X-Authentication-Digest` (header-based, matches the current `Extract`).
- Resolution: header-only `Extract` works for R2 and CP only. L payment and withdrawal DMNs need the reviewed body-field extension (PLATFORM CHANGE as already framed in the 2026-10-18 matrix). The content type and the exact byte form of the body for the L MAC are unverified, so the sandbox must confirm whether the covered values are taken from decoded parameters (with `+` -> space) rather than raw bytes.

### N-1 merchant reference vs covered fields; positive-binding status query
- L payment DMN: covered set is only `totalAmount, currency, responseTimeStamp, ppp_TransactionID, Status, productId`. `merchant_unique_id`, `clientUniqueId`, `clientRequestId` are NOT covered, so the DMN alone does not bind our reference (INCOMPATIBLE for DMN-driven success, as predicted).
- A positive-binding status query EXISTS:
  - L `getTransactionDetails`, input `transactionId` or `clientUniqueId` + signed request; returns `transactionDetails.transactionId`, `.clientUniqueId`, `.transactionStatus`; but NO top-level amount/currency (second read confirms). So signed tx id -> our reference + status is bound; amount and currency can only come from the signed DMN fields (`totalAmount`, `currency`), which ARE covered. Combined rule: MAC-valid DMN gives (txId, amount, currency, status, time); `getTransactionDetails(transactionId)` must return our `clientUniqueId` and the same status; compare amount/currency to our order. This meets "binds signed transaction id to OUR reference + amount + currency before financial effect" only with the amount coming from the DMN leg. Caveat: DMN `currency` is "Currency selected by the customer that was sent to the payment page", `totalAmount` is the sum of items; with DCC/MCP these can differ from the charged order currency (see `convertedAmount`, `currencyConversion.*`); mismatch must park.
  - L `getPaymentStatus` returns amount, currency, `clientUniqueId`, `transactionStatus` but only for the same live `sessionToken`; unusable for later reconciliation ("session expired").
  - R2 Data API `GET /entities/{processing-entity-id}/transactions/{transaction-id}` returns `merchantTransactionId`, `processedAmount`, `processedCurrency`, `transactionStatus`, `transactionId` in one call: full positive binding. Beta.
- R2 webhooks: HMAC over the full body, which includes `merchantTransactionId` (listed among top-level payload fields), so N-1 does not arise.
- Withdrawal DMN: all parameters incl. `merchantUniqueId` are covered (but see P).

### N-2 algorithm options
- L payment DMN: "SHA-256 or MD5 ... depending on the SiteId configuration"; "Although MD5 encryption is supported, SHA-256 is recommended." Per-site. Whether the platform can verify the site's setting is NOT VERIFIED (no API for reading it). Withdrawal DMN, CP, `getTransactionDetails`/`getPayoutStatus`/`openOrder` requests: SHA-256 stated. R2 webhook: HMAC-SHA256 only. Resolution: SHA-256 is selectable per site; registration must record and the vendor must confirm the site is SHA-256 (question U1).

### G-03 session/order id vs transaction id lifecycle (L)
- `openOrder` returns `sessionToken` (36 chars, "The session identifier to be used by the request that processed the newly opened order") and `orderId` ("The order ID provided by Nuvei."). `transactionId` is only created when the payment is processed ("The Gateway transaction ID.") and is the id used by DMN (`TransactionID`), `getTransactionDetails`, refund (`relatedTransactionId`).
- The DMN has TWO provider ids: `PPP_TransactionID` ("A unique 64-bit number that identifies the Nuvei payment page transaction.") and `TransactionID` ("... fiscal transaction in the Nuvei payment gateway"); the checksum covers `ppp_TransactionID` (payment page tx), not `TransactionID`.
- Session token lifetime: not stated in API 1.0 (Simply Connect 2.0: "usually about fifteen minutes", per #38).
- Order id vs transaction id relationship: "Not explicitly stated" in the visible text. Resolution: the stable provider reference at `Deposit` return is NOT available (no transaction id yet); the platform must hold our own `clientUniqueId`/`orderId` as the initial reference and bind `transactionId` at the first verified event (PLATFORM CHANGE, as predicted). Which of `PPP_TransactionID`/`TransactionID` is the stable one for statements/refunds is NOT VERIFIED (the refund page uses the gateway `transactionId`).

### G-05 refund / chargeback stages
- Partial refunds and multiple partial refunds are supported (L row). Chargebacks: money moves at First Chargeback; representment can reverse; `Retrieval` events carry no money; CP `ChargebackStatusCategory` has Regular, cancelled, Duplicate, RDR-Refund, Soft_CB; no "final" marker found. Disputes API status table (~90 codes) gives stage info only in R2 for Nuvei-direct-acquired Visa/MC. Resolution: park partial and staged events as unsupported P1 (as predicted); "final debit" needs a vendor answer (question U8).

### G-07 file reconciliation
- Settlement data: SFTP/email scheduled reports only (Settlement Summary, Movement, Balance). Transaction-level pull exists in R2 (Data API list, 30 per page, date range, `merchant_transaction_id` filter). File timing: GMT+2 day, T+1 to T+3 depending on acquirer model, 15-day SFTP retention, empty-file caveat. Resolution: PLATFORM CHANGE (file-ingestion adapter); read-only credential for the SFTP exists only as "the credentials Nuvei emails" (not a scoped read-only concept), and no read-only API key is documented.

### G-08 credential fields
- L: `merchantId`, `merchantSiteId`, `merchantSecretKey`. R2: `processingEntityId`, `x-api-key` (Operations or Dispute type), webhook shared secret, optional DMN key at lowest entity level. SFTP: host, port, user, private key, password. Resolution: multi-field handle needed (PLATFORM CHANGE small).

### G-09 payout notification scheme differs?
- Yes in L: payment DMN (prefix secret, six covered values, `advanceResponseChecksum`) vs withdrawal DMN (suffix secret, all names+values in sent order, `checksum`) vs CP-EVENT (header, JSON values, prefix). Which one is used for the outcome of a `/payout` call is NOT VERIFIED. R2 payout uses the same R2 webhook (inferred from "Nuvei sends a webhook", scheme not restated on the payout page).

### G-10 payout destination model
- Hosted capture gives a UPO (opaque id) through `accountCapture` with `userTokenId` we choose. Raw alternatives exist and must be disabled by us (cardData, apmData, R2 accountNumber/routingNumber). Binding of UPO to `userTokenId`, immutability, and merchant visibility of captured details are NOT stated. `getPayoutStatus` echoes `userPaymentOptionId` and `userTokenId` (so destination echo is checkable). Resolution: see KT3.

## 4. Kill tests

### KT1 signed webhook can be bound to our merchant reference before money moves
Result: PASS WITH PLATFORM CHANGE.
- R2 webhook: PASS as documented (HMAC over the whole body includes `merchantTransactionId`; "Nuvei recommends that merchants use `merchantTransactionId` in the webhook for mapping webhooks to transactions."), but the concatenation of H and T is unspecified and the product is Beta.
- L payment DMN: the reference is not signed ("merchant_unique_id" absent from the checksum list), so the DMN is not self-binding. Binding is achieved only by the follow-up signed `getTransactionDetails(transactionId)` (returns `clientUniqueId`, status) combined with the signed amount/currency from the DMN. Evidence: getTransactionDetails output rows `transactionDetails.clientUniqueId`, `.transactionStatus`; DMN checksum list `totalAmount, currency, responseTimeStamp, ppp_TransactionID, Status, productId`. Platform change: DMN-body-field extraction (G-01) + a mandatory bind-by-query step before effect. Caveat: `ppp_TransactionID` is the payment-page tx id while `getTransactionDetails` takes the gateway `transactionId`; the mapping between the signed id and the queryable id is NOT VERIFIED (question U3). If the two ids cannot be mapped by a signed field, KT1 on L falls to FAIL.

### KT2 replay protection achievable
Result: PASS WITH PLATFORM CHANGE.
- L payment DMN: `responseTimeStamp` is inside the checksum (GMT, `yyyy-MM-dd.HH:mm:ss`). Window enforceable by the platform; the same field is covered in withdrawal DMN (all params). No nonce.
- R2: Unix timestamp T in the HMAC input; Nuvei says stale messages should be rejected; tolerance not documented; platform applies its own 10 min.
- CP-EVENT: no named timestamp in the checksum; payload contains `EventDateUTC` but whether it is a covered value is not guaranteed by the text -> UNKNOWN.
- Platform change: parser for the L timestamp format; policy for legitimately delayed redeliveries (retry schedule NOT VERIFIED) - recover via QueryStatus.

### KT3 payout destination bound to the player and immutable without weakening our controls
Result: FAIL as documented; PASS WITH PLATFORM CHANGE only if the vendor confirms UPO binding and immutability.
- Evidence for possible: hosted capture through `accountCapture` returning a UPO ("Nuvei stores the captured details in a `userPaymentOptionId`"); `userTokenId` is mandatory on capture and payout; `getPayoutStatus` echoes `userPaymentOption.userPaymentOptionId` and `userTokenId`.
- Evidence missing: "The page does not say whether a UPO can be edited, updated, or deleted"; binding of UPO to `userTokenId` "not explicitly" stated; also the same payout call accepts `cardData`/`externalToken` instead of a UPO, and `/addUPOAPM` accepts merchant-supplied account data. The control that makes the destination immutable (UPO read-only; payout refused if `userTokenId` differs from the UPO owner) is therefore not shown to be enforced by Nuvei; the platform would have to enforce it by storing (UPO id, player, brand, attempt) and verifying the echo after the fact, which detects but does not prevent. Prevention needs vendor confirmation (U10/U11).

## 5. Unresolved questions for the vendor
- U1 Can we read or confirm per site that DMN hashing is SHA-256 only (MD5 disabled)? Is there a switch to refuse MD5?
- U2 Payment DMN transport: HTTP method (GET or POST), Content-Type, where `advanceResponseChecksum` and `responseChecksum` travel, and the formula of `responseChecksum`. Is the checksum computed over decoded values (`+` to space) or raw?
- U3 In the payment DMN, `checksum` covers `ppp_TransactionID`; which id is accepted by `getTransactionDetails` (`TransactionID` or `PPP_TransactionID`), and how do the two map?
- U4 Retry schedule, timeout and expected HTTP response for payment, withdrawal, payout and CP-EVENT DMNs; do re-sent DMNs keep the original `responseTimeStamp`?
- U5 Which DMN format (payment, withdrawal, R2 webhook) carries the result of a `/payout` and of an `/accountCapture`, and what is its checksum? Where does the withdrawal `checksum` travel and is it excluded from its own input? What is the separator between names and values?
- U6 R2 webhook: order and separator of H and T in the HMAC input; encoding of H (hex/raw); timestamp tolerance; whether payout and dispute webhooks use the same headers; retry and dedup identifiers.
