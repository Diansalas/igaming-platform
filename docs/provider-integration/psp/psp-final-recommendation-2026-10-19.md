## 1. Verified provider facts (the ones that decide)
### Nuvei (three families: LEGACY REST 1.0 + DMNs, REST 2.0 (labelled Beta), Control-Panel event DMNs)
- Payment DMN checksum `advanceResponseChecksum`: merchant secret **prepended** to `totalAmount, currency, responseTimeStamp (GMT), ppp_TransactionID, Status, productId`; SHA-256 **or MD5 "depending on the SiteId configuration"**; the old `responseChecksum` is deprecated. **Not covered:** `clientUniqueId`, `merchant_unique_id`, `clientRequestId`. Delivery method/content type/encoding are **not stated** on the page.
- `responseTimeStamp` is inside the checksum (signed timestamp present). No retry schedule documented.
- Status queries: `getTransactionDetails` (by `transactionId` or `clientUniqueId`) returns our `clientUniqueId`, `transactionId`, `transactionStatus` but **no amount/currency**; `getPaymentStatus` returns amount/currency/reference but only within the live `sessionToken`; REST 2.0 Data API `GET /entities/{id}/transactions/{id}` returns `merchantTransactionId`, `processedAmount`, `processedCurrency`, `transactionStatus`, `transactionId` (Beta).
- REST 2.0 webhook: headers `X-Authentication-Timestamp` (Unix seconds) and `X-Authentication-Digest`; HMAC-SHA256 over SHA-256(body) combined with the timestamp (combination order/separator **not specified** on the page); body contains `merchantTransactionId`; "too far in the past or future ... rejects"; **no tolerance, no retry schedule**.
- Withdrawal DMN: different scheme (secret **appended**, all parameters in sent order, parameter `checksum`, location not stated). Control-Panel chargeback event: header `checksum`.
- Payout: `/payout` destination is `userPaymentOptionId` (UPO from hosted `accountCapture`, DMN `type=ACCOUNT_CAPTURE` carrying `user_token_id` + `userPaymentOptionId` + `responseTimeStamp` + `advanceResponseChecksum`, scheme not explained) **or** clear `cardData` / `externalToken`; merchant-supplied account data exists (`addUPOAPM` apmData; REST 2.0 `accountNumber`/`routingNumber`). Not stated: UPO↔`userTokenId` binding, UPO edit/delete, merchant read of captured details. `getPayoutStatus` (by `clientRequestId`) returns amount, currency, status and echoes UPO + `userTokenId`.
- Refunds: partial and multiple partial supported; async pending then DMN. Chargebacks: money moves at first chargeback, representment can reverse; **no "final" marker**.
- Reports: Control Panel / SFTP files (GMT+2 day, T+1..T+3, 15-day retention); no settlement API; REST 2.0 Data API pulls transactions (30/page). No read-only credential concept documented.
- Credentials: legacy `merchantId, merchantSiteId, merchantSecretKey`; REST 2.0 `processingEntityId, x-api-key, webhook secret`; SFTP host/port/user/key.
- Sandbox: separate integration environment; account issuance, sandbox credentials and gambling-merchant approval are **not self-service and not documented**; payouts require a Nuvei Support request. Idempotency: legacy depends on a per-merchant `clientRequestId` uniqueness setting; REST 2.0 idempotency 15 minutes.

### Adyen
- Standard webhook HMAC-SHA256 (hex key decoded, Base64): `pspReference:originalReference:merchantAccountCode:merchantReference:value:currency:eventCode:success`; signature in the JSON body `additionalData.hmacSignature` (other families: header `hmacsignature`). **Our reference and amount are signed. No timestamp or nonce is signed**; `eventDate` is unsigned; no freshness mechanism is documented. No ":" escaping documented.
- Status: `GET /sessions/{id}` needs the browser's `sessionResult` (page says not to poll); **no lookup by reference or pspReference found**.
- Payouts: classic Payout API closed to new integrations; Transfers API v4 needs a balance platform/contact with Adyen (not self-service); `POST /transfers` accepts a raw `counterparty.bankAccount` per payout (holder name/address/DOB); stored transfer instruments are mutable (PATCH keeps the id); card payouts via `storedPaymentMethodId`. `booked` is not final (`returned`/`failed` can follow). Brazil/Mexico absent from the bank-payout country table; Pix/SPEI payouts NOT VERIFIED. Transfer webhooks: no documented signature scheme.
- Chargebacks: pages disagree on when funds move; `CHARGEBACK_REVERSED` not final; no "final debit" definition. Reports: files over HTTP GET with a Report user + `REPORT_AVAILABLE` webhook; no JSON statement API; SFTP not verified.
- Idempotency: `Idempotency-Key` header, 64 chars, 7–14 days, company-level. Webhooks: 2xx within 10 s, retries up to 30 days; no published IP list. Credentials >= 6 values per tenant. Free self-service test account; live account needs approval and contract. Gambling eligibility **NOT VERIFIED from documentation**.

## 5. Recommendation
**First PSP: Nuvei, conditional (AMBER).** Justification: it is the only candidate that satisfies the signed-timestamp rule as written, no kill test is an outright FAIL for it (KT3 fails only for the hosted-capture UPO variant, and the merchant-supplied-details variant is a documented alternative), and every gap has a bounded, provider-neutral platform change that Adyen would also need (G-01, G-03, G-07, G-08). Adyen is technically cleaner on reference binding and on the destination model, but fails KT2 as documented, has no status pull, and its payout rail is not self-service; choosing it would require **weakening a rule** (signed timestamp) first, which the brief forbids.
Conditions to hold before any adapter code, all answerable in the Nuvei sandbox/vendor reply: (1) generation choice: REST 2.0 (header scheme, reference signed, Data API) vs legacy (needs G-01 and bind-by-query; question U3 must be YES); (2) a payout path where **our** destination is passed per payout (apmData/accountNumber) for the target EU/LATAM methods, or written confirmation that a UPO is bound to its `userTokenId` and immutable and that a payout with another player's UPO is refused; (3) SHA-256-only site; (4) the payout result notification scheme; (5) a defined "final" chargeback event; (6) written REST 2.0 GA/deprecation outlook.
If (2) fails for the target markets, deposits can still proceed (KT1, KT2 pass) but **payouts do not**; then assess a third PSP **for the payout rail only**, and revisit the replay rule decision before choosing Adyen or Checkout.com.

## 6. Work split (nothing started)
- **Required adapter work (Nuvei):** closed event/status mapping; `QueryStatus` via the chosen status API; signature verifier per event family; SHA-256 pin (refuse MD5); reference binding (store our `clientUniqueId`/`merchantTransactionId`, bind transaction id at first verified event); payout request builder that forbids `cardData`/`externalToken`; unsupported-event parking (partial refund, staged chargeback, control-panel transactions); idempotency via `clientRequestId`; statement/file parser; credential handle mapping; conformance suite `PSP-C-nn`.
- **Required platform changes (each reviewed by security; money paths by ledger-finance):** PC-1 body-field signature extraction (G-01; avoidable with REST 2.0); PC-2 confirm-by-query step before financial effect; PC-3 timestamp formats + delayed-redelivery policy; PC-4 two-reference lifecycle (G-03); PC-5 multi-field credential handle (G-08); PC-6 per-event-family scheme (G-09); PC-7 file-ingestion statement adapter and read-only credential rule (G-07/G-04); PC-8 payout destination rule (G-10): destination in our `payoutinstrument`, vault tokens only if the vendor proves binding + immutability.
- **Commercial/onboarding:** Nuvei issues the test account (not self-service), payouts need a Support request, gambling-merchant approval undocumented; Adyen test account is free, live account needs approval + contract and payouts need Adyen contact. - **Unresolved questions:** Nuvei U1 SHA-256-only; U3 `ppp_TransactionID` -> `transactionId` mapping; REST 2.0 H+T combination order and timestamp tolerance; payout DMN scheme; UPO binding/immutability/deletion; payout methods supporting merchant-supplied details; retry schedule; final chargeback marker; REST 2.0 GA date; read-only SFTP credential.
