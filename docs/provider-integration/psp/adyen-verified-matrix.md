## 0. Evidence rules and caveats (read first)

- VERIFIED = stated on an official `docs.adyen.com` page fetched with WebFetch in this task. WebSearch was used only to discover URLs; anything known only from a search snippet is marked NOT VERIFIED (search pointer only).
- WebFetch returns text produced by a small extraction model with a quote-length cap (about 125 characters). Quotes below are what that extractor returned as exact text; longer passages came back as paraphrase and are labelled `(para)`. Security-critical items (D, E, F, H, M, N-Q) were fetched at least twice with different prompts, or from two different pages.
- Pages are undated; "version seen" is the API version the page states. Several large API Explorer pages were truncated by the fetcher (155k characters); response schemas of `/payments` and `/payments/details` were NOT readable (see section 1 and Unresolved questions).
- `www.adyen.com` (restricted-business list, legal terms) is outside the allowed host and was not fetched. Gambling eligibility is therefore NOT VERIFIED from docs.

## 3. Resolution of findings

**G-01 (signature location vs header-only extraction).** Confirmed. For Standard webhooks "the signature is included in the additionalData field" (page #1), and is verified over eight extracted JSON values, not over the raw body. Header signatures (`hmacsignature`, `protocol`) exist only for "other types of webhooks, although rare". A header-only `Extract(Inbound)` cannot serve Standard webhooks. Outcome: PLATFORM CHANGE (reviewed extension: scheme reads a parsed body field; the same scheme builds the canonical string from parsed fields; reject duplicate keys and multiple `notificationItems`; the body is not integrity-protected beyond the eight fields).

**N-1 (merchant reference vs covered fields; query that binds).** Resolved by the signature: `merchantReference`, `value`, `currency`, `pspReference`, `merchantAccountCode`, `eventCode`, `success` are all covered (page #1). There is no documented status query by reference or pspReference; `GET /sessions/{id}` needs the browser's `sessionResult` and is one-shot (page #11). Residual risk: uniqueness of `reference` per merchant is not documented as enforced; the ":" delimiter has no documented escaping. Our rule: reference charset without ":" and "\\", unique constraint on our side.

**N-2 (algorithm options).** Only HMAC-SHA256 is documented ("The SHA256 function.", header `protocol` "HmacSHA256"). No MD5 or other option appears on the pages read. COMPATIBLE.

**G-03 (session/order id vs transaction id lifecycle).** Confirmed. We hold a session `id` at creation (page #11), the webhook carries `pspReference` per attempt (and a refused session may allow several attempts: session status "refused: ... too many refused payment attempts"), and our `reference` is echoed as `merchantReference`. No webhook field linking to the session id was seen (envelope item fields not readable). Outcome: PLATFORM CHANGE per the reviewed reference-binding rule: the stable provider reference at `Deposit` return cannot be the pspReference; bind by `merchantReference`, record pspReference on first success.

**G-05 (refund/chargeback stages).** Confirmed. Refund is asynchronous with REFUND_FAILED; partial refunds exist; chargebacks have eight event stages and a won credit (CHARGEBACK_REVERSED) that is itself "not final" (page #31). Adyen's own pages disagree on whether money moves at NoC (#29 vs #27/#28). Adapter maps a full-amount CHARGEBACK `success=true` only; everything else parks. Final-debit identification is not defined by Adyen (question Q4).

**G-07 (file reconciliation).** Confirmed. Reports are files fetched by HTTP GET with a Report user (role "Merchant Report Download"), announced by REPORT_AVAILABLE. No JSON statement API was found on the pages read. SFTP report delivery: NOT VERIFIED. Needs a file-ingestion adapter and a settle-lag declaration (report only lists settled/paid-out payments; batch timing follows payout frequency).

**G-08 (credential fields).** Confirmed: API key, merchant account code, client key (browser-side), live URL prefix, HMAC key per webhook endpoint, report credential, plus a separate payout credential on another host and a balance account id. PLATFORM CHANGE (multi-field handle).

**G-09 (payout notification scheme differs?).** UNKNOWN. Payout/transfer webhooks are a different family (`balancePlatform.transfer.*`, objects `data`, `environment`, `type`), no signature text on the pages read. Almost certainly differs from the Standard scheme; presence of a timestamp NOT VERIFIED. Legacy `PAYOUT_*` events are deprecated for new integrations.

**G-10 (payout destination model).** Bank: raw `counterparty.bankAccount` is accepted per transfer, so the platform can hold the destination and send it each time (compatible with ADR 0095 s4.5 echo, provided the webhook echoes `counterparty`, NOT VERIFIED). Stored transfer instruments are mutable (PATCH keeps the id) and must not be the canonical destination. Card: token bound to `shopperReference` by convention only; raw card only for fully PCI-compliant merchants.
