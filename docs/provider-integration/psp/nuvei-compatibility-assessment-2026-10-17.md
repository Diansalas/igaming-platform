## 2. What the summaries say (by topic)
| Topic | SEARCH-SUMMARY finding |
|---|---|
| Auth / session | Server-to-server REST starts with `/getSessionToken` (token valid 15 min); Web SDK / Simply Connect start with `/openOrder`. Both requests carry a SHA-256 `checksum` = hash(merchantId, merchantSiteId, clientRequestId, [amount, currency,] timeStamp, merchantSecretKey). `/openOrder` must come from our backend. |
| Payment | `/payment` request; the result is delivered by DMN (webhook) to `urlDetails.notificationUrl` (REST 2.0: `urlDetails.webhookUrl` in the request). |
| DMN integrity | Payment DMNs carry `advanceResponseChecksum` = SHA-256 **or MD5 depending on the site's configuration** over: secret key + `totalAmount`, `currency`, `responseTimeStamp` (GMT), `ppp_TransactionID`, `Status`, `productId` (fixed order; spaces arrive as `+`). The checksum travels as a **body/query field**, not a header. The merchant reference (`clientUniqueId`) is **not listed** among the covered fields. No nonce or freshness rule is documented. |
| DMN delivery | HTTPS POST with name/value parameters; APM payments send a second DMN with the same data and the final status (at-least-once, duplicates expected). Withdrawal DMNs reportedly use a **different** scheme (name=value pairs with the secret appended) (THIRD-PARTY AsyncAPI summary). |
| Refund / void | `/voidTransaction` before settlement, `/refundTransaction` after; async providers return `status=PENDING` with the final result in a later DMN. REST 2.0 exposes `POST /payments/{id}/refunds`. Control-Panel-generated void/refund/settle produce their own DMN type. |
| Chargeback | DMN type covers new disputes and later status updates; a separate pre-chargeback (Ethoca) alert DMN can trigger an automatic refund by rule. |
| Payout | `/payout` takes a `userPaymentOptionId` (UPO). A UPO is created by a **hosted account-capture flow** (`/accountCapture` returns a URL; a DMN `type=ACCOUNT_CAPTURE` returns the new UPO). Card payouts with raw card data need a PCI-certified merchant. The response carries `transactionStatus`/`status`/`errCode` and a payout DMN follows. The full payout status list and payout-DMN fields were not found. |
| Reporting | Settlement/reconciliation is via reports (Settlement Summary, Transaction, Movement Report) scheduled and delivered as files (XLS/PDF/CSV, SFTP on request). **No documented programmatic transaction-history/statement API was found.** |
| Sandbox | Nuvei issues a separate integration (test) account on onboarding (welcome e-mail with an activation link; control panel `sandbox.nuvei.com`); REST 2.0 sandbox hosts `api-sandbox.nuvei.com/{payment-api,sdk-api,account-api,data-api}`; test cards incl. 3DS scenarios; Postman collections. Nothing found showing self-serve sign-up. |
| API generations | Two: legacy REST (`/getSessionToken`, `/refundTransaction`) and REST 2.0 (`/payments`, `/payments/{id}/refunds`, `urlDetails.webhookUrl`). Which one carries payouts, account capture and the signed webhook is **not established**. |

## 3. Fit against the platform contract (requirement → finding → verdict)
Platform requirements and gap ids G-01..G-08 are those of `provider-neutral-mapping.md` / `nuvei-evaluation.md`.

| # | Platform requirement | Finding (SEARCH-SUMMARY) | Verdict |
|---|---|---|---|
| 1 | Hosted/redirect card capture, no PAN on our servers (CLAUDE.md) | Web SDK / Simply Connect / hosted flows exist; account capture is hosted | **FIT (likely)** — confirm in sandbox that no PAN transits our backend |
| 2 | Signed timestamp inside the MAC, replay window ≤ 10 min (`scheme.go:261`) | `responseTimeStamp` is a covered field | **FIT (likely)**: G-02 is *not* blocking if the timestamp is in the covered set; the platform enforces the skew itself |
| 3 | Signature readable by `Extract` (**header-only**) | Checksum is a **body/query field** (form parameters) | **GAP G-01 CONFIRMED (platform-wide, blocking for this PSP)**: needs a reviewed extension so a scheme may read the signature from a parsed body field of the raw bytes. Security + architect review. Not a Nuvei-specific hack: any form-encoded webhook PSP needs it |
| 4 | MAC strength | SHA-256 or **MD5 per site configuration** | **CONDITION**: site must be configured SHA-256; adapter refuses MD5 (algorithm pinned at registration, fail closed); verify in sandbox |
| 5 | Merchant reference echoed and *bound* | `clientUniqueId` echoed but apparently **outside the checksum** | **SECURITY FINDING N-1 (blocking until resolved)**: a captured valid DMN could be replayed with an altered unsigned reference to attribute a success to another intent. Mitigations that keep our model: bind on signed fields only (`ppp_TransactionID` + amount + currency + status), and treat the DMN as a **trigger**, confirming through `QueryStatus` (status API) before the platform applies it; the platform already declares "success only via verified callback or QueryStatus". Needs the `callback-triggers-query` pattern and its review |
| 6 | Per-tenant key binding | Secret is per merchant site; separate merchant site per tenant is commercial | **FIT if** one Nuvei merchant site/secret per tenant/brand; confirm signing key is per site |
| 7 | One stable provider reference known at `Deposit` return (G-03) | Session token / order id at start; `ppp_TransactionID` assigned at payment | **GAP G-03 CONFIRMED (platform-wide)**: two-reference lifecycle → needs the reviewed reference-binding rule (platform stores order/session id as the attempt's merchant reference and the transaction id on first verified event); ledger-finance review |
| 8 | QueryStatus success carries amount + asset | Not established | **UNVERIFIED** (sandbox) |
| 9 | Idempotent submission | `clientRequestId` exists; duplicate semantics not found | **UNVERIFIED** (sandbox) |
| 10 | Closed event set; unknown → P1 unsupported, never applied | Many DMN types (payment, refund, chargeback, pre-chargeback, control-panel generated, account capture, payout, dispute updates) | **FIT by construction** (fail closed); the mapping table must classify each |
| 11 | Two signing schemes under one provider | Payment DMN vs withdrawal DMN reportedly differ | **GAP G-09 (new, platform-wide, small)**: a provider needs one scheme per event family (or the payout side registers as a separate provider id) |
| 12 | Payout to a platform-bound destination with echo semantics (ADR 0095 s4.5, `payoutinstrument`) | Payout goes to a **provider-vaulted UPO** created by a hosted capture flow, not to bank details we hold | **GAP G-10 (new, platform-wide, significant)**: needs a destination kind "provider token" bound to the player and brand at capture time (the capture DMN is the binding event), with the same four-eyes/destination-integrity guarantees; or use a payout method that accepts IBAN-type details (if the API offers it). Security + ledger-finance + architect review. Do not weaken destination integrity to fit |
| 13 | Whole-deposit `deposit_reversal` only on a final debit; partial refunds / dispute stages / won chargebacks not emitted | Partial refunds, async refunds, dispute updates, pre-chargeback alerts exist | **GAP G-05 CONFIRMED**: adapter maps only the final debit; the rest park as unsupported (P1) until a reviewed partial-reversal design exists |
| 14 | Read-only time-ordered statement source (A11) | File-based reports (SFTP/CSV), no statement API found; SFTP login is separable from the API secret | **GAP G-07 CONFIRMED**: file-ingestion adapter; settlement-currency field G-06 likely; per-provider settle lag declaration needed (LF-A11-2). The SFTP credential is naturally read-only (helps G-04) |
| 15 | Single secret + one account id per credential handle (G-08) | Needs merchantId, merchantSiteId and secret key (+ SFTP credentials) | **GAP G-08 CONFIRMED** (small, platform-wide) |
| 16 | Commercial eligibility (iGaming, Anjouan, EU/LATAM methods) | Not answerable from documentation | **OWNER/COMMERCIAL** (OQ-1) |

## 4. Viability statement
**Nuvei is CONDITIONALLY VIABLE and NOT YET PROVEN.** Nothing found disqualifies it on its face; the signed timestamp fits. But the integration needs **five reviewed platform-wide additions that any real PSP will also need** (not Nuvei hacks): G-01 body-field signature extraction, G-03 two-reference lifecycle, G-08 multi-field credentials, G-09 one scheme per event family, and the larger G-10 provider-vaulted payout destinations, plus G-07 file-based statements and the N-1 confirm-by-query rule. None of these may be built from search summaries alone, because each would encode an unverified field list or flow. The incompatibility test of the owner's rule ("if Nuvei cannot satisfy a required security or financial contract, evaluate another PSP") is **not yet triggered**; it will be triggered if the primary documentation shows (a) no usable payout destination model (G-10 impossible without weakening destination integrity), (b) no signed timestamp, or (c) no way to confirm a DMN by status query.

## 5. Security assessment (threat view, pre-implementation)
| Id | Threat | Control required before any adapter ships |
|---|---|---|
| N-1 | Unsigned merchant reference → misattribution of a success | Bind on signed fields + confirm by `QueryStatus`; amount/asset mismatch → existing dispute park |
| N-2 | MD5 checksum acceptable by site config | Pin SHA-256; refuse MD5 at registration; sandbox check |
| N-3 | Replay of a valid DMN | Platform skew check on the signed timestamp + existing idempotency on (provider, transaction id, status); duplicates are expected (second DMN with final status) |
| N-4 | Form-encoded body parsing differences (`+` for spaces, encoding, duplicate parameters) | Verify the MAC over a canonical re-serialisation per the vendor's rule only after the reviewed G-01 design; reject duplicate keys; fuzz tests |
| N-5 | Tenant confusion (one DMN accepted for another tenant) | Per-tenant secret/site; route carries tenant; signed account/site id if covered |
| N-6 | Payout destination substitution through the vault flow | Capture DMN must be verified, bound to player+brand+attempt, immutable after binding, step-up/four-eyes on first payout to a new token (existing controls), echo declared |
| N-7 | Control-panel-generated transactions (operator actions in the PSP console) change money outside our system | Appear as DMN/statement lines → unsupported-event P1 or reconciliation findings; never applied silently |
| N-8 | Secrets: merchant secret key, SFTP credentials | `providercred` handles; rotation runbook; never logged (existing guards) |

## 6. Sandbox: what can be tested, and what blocks it
Needed from Nuvei (commercial/credential action): an **integration (test) account** → merchantId, merchantSiteId, secret key, configured notification URL(s), checksum algorithm = SHA-256, enabled methods/currencies for the target brands, a payout-enabled test configuration, an SFTP/report test feed. Without it **nothing can be conformance-tested**. Testable in sandbox once issued: deposit via hosted flow, 3DS scenarios, DMN delivery/duplicates/second-DMN-final-status, refund (sync/async), void, status query, account capture + payout of a UPO (if enabled), report format. Likely **not** testable: real chargebacks, real banks, production limits, iGaming merchant approval.
